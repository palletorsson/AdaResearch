In earlier chapters a body was one shape, made once. In this chapter a body is a **history**. You start with one row of cells. A **rule** makes the next row from that one, then the row after that, and so on. You keep every row, and each new row stands one step higher and one step further back than the last. The rows together make a **stair**, and you can walk up it.

The new programming idea in this chapter is **two buffers**: you read the old row from one array and write the new row into another. You will find out why you need that by getting it wrong first.

## 13.2 One row

*Picture: a single lime tile. Under it, the printed row: seventeen numbers, all 0 except one 1 in the middle.*

Start with one row. Here is the whole script for this step:

```gdscript
extends Node3D

const Look := preload("res://supplied/look.gd")

@export var n := 17                    # cells in a row
@export var cell := 0.4                # metres: a cell's width and depth
@export var rise := 0.15               # metres: a tile's thickness, and how much higher the next row stands

var now := PackedByteArray()    # the row read: one byte for each cell, 0 or 1
var tile := BoxMesh.new()       # one mesh for every cell

func _ready() -> void:
	tile.size = Vector3(cell * 0.9, rise, cell * 0.9)
	tile.material = Look.paint(Look.BODY)
	now.resize(n)
	@warning_ignore("integer_division")
	now[n / 2] = 1
	lay_row()

func lay_row() -> void:
	var row := Node3D.new()
	add_child(row)
	var tiles := MultiMesh.new()
	tiles.transform_format = MultiMesh.TRANSFORM_3D
	tiles.mesh = tile
	tiles.instance_count = now.count(1)
	var drawn := MultiMeshInstance3D.new()
	drawn.multimesh = tiles
	row.add_child(drawn)
	var k := 0          # which tile comes next
	for i in n:
		if now[i] == 1:
			tiles.set_instance_transform(k, Transform3D(Basis(), Vector3(x_of(i), rise / 2.0, 0.0)))
			k += 1
	print(now)

func x_of(i: int) -> float:
	return (i - (n - 1) / 2.0) * cell
```

Some words first.

- A **cell** is one place in a row. It holds 1, meaning *live*, or 0, meaning *dead*.
- A **row** is cells side by side. Here there are `n = 17` of them.
- A **buffer** is an array that holds one row. Our buffer is `now`, a `PackedByteArray` of seventeen bytes, one per cell. `now.resize(n)` makes it seventeen bytes long, and every new byte starts at 0.
- The middle cell, `now[n / 2]`, which is cell 8, is set to 1. That cell is the **seed**: everything that follows grows from it. `n / 2` divides one integer by another, so the result is cut down to an integer (17 / 2 is 8). Godot warns about that in case you meant a fraction. `@warning_ignore("integer_division")` on the line before tells it that here you meant it.
- A **tile** is what a live cell looks like: a flat box a little narrower than a cell (`cell * 0.9`), so that neighbouring tiles show a seam between them, and `rise` thick. [guess] `Look` is the supplied course look, and `Look.paint(Look.BODY)` returns the course's material for a body, the lime colour.

`lay_row()` draws the row. Instead of making one mesh node for every live cell, it uses a single `MultiMesh`, which draws many copies of one mesh. `now.count(1)` counts how many bytes in the row are 1, and that is how many copies we need. The counter `k` says which copy to place next. Each live cell `i` gets a copy at `x_of(i)`, raised by `rise / 2.0` so that the tile sits on the floor rather than half inside it.

`x_of(i)` turns a cell number into a position in metres. It centres the row: cell 8 lands at x = 0, cell 0 at −3.2 m and cell 16 at +3.2 m.

`print(now)` writes the row to the Output panel, so you can check the numbers as well as the picture.

Press Play. You should see one lime tile and, in the Output panel, a row of seventeen numbers with a single 1 in the middle.

## 13.3 The rule

*Picture: the eight neighbourhoods with Rule 90's answers. Beside them, a floor that leans to the right.*

A cell's **neighbourhood** is three cells: the one on its left, the cell itself, and the one on its right. Each of them is a **bit**, 0 or 1. Three bits can be arranged in exactly eight ways, from 111 down to 000. A **rule** gives one answer, 0 or 1, for each of the eight. That answer is the cell's state in the next row.

Here is Rule 90:

| left, self, right | 111 | 110 | 101 | 100 | 011 | 010 | 001 | 000 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Rule 90 answers | 0 | 1 | 0 | 1 | 1 | 0 | 1 | 0 |

Read the bottom row from left to right as one binary number: 01011010. In decimal that is 64 + 16 + 8 + 2 = 90. **The rule is its own name.** Every rule from 0 to 255 is a different set of eight answers, and its number is those answers written in binary.

To use that in code, turn the neighbourhood into a column number. Read left, self, right as a three-bit binary number:

```
index = left * 4 + self * 2 + right
```

So 111 is index 7, 110 is 6, and so on down to 000, which is index 0. The table lists the columns from 7 on the left to 0 on the right, which is also the order of the bits in the binary number: bit 7 first, bit 0 last. The answer for a neighbourhood is therefore bit number `index` of the rule. You read it like this:

```
(rule >> index) & 1
```

`>>` shifts the rule's bits `index` places to the right, so the bit you want lands in the lowest place. `& 1` keeps only that lowest bit and throws the rest away. For example, the neighbourhood 110 has index 6, and 90 shifted right by 6 is 1 (90 is 1011010, and dropping six bits leaves 1). `1 & 1` is 1, which matches the table.

Now grow the script. Add three variables:

```gdscript
@export_range(0, 255) var rule := 90
@export var rows := 11
var made := 0
```

`@export_range(0, 255)` is an export that the Inspector limits to whole numbers from 0 to 255, because that is every possible rule. `rows` is how many rows to build in total. `made` counts the rows already laid.

Change `lay_row()` so that each row stands further back than the last: put the row at z = `-made * cell`. Print the row together with its number, and then count up. [guess] At this stage the changed lines of `lay_row()` look like this:

```gdscript
	var row := Node3D.new()
	row.position = Vector3(0.0, 0.0, -made * cell)
	add_child(row)
	...
	print(made, " ", now)
	made += 1
```

End `_ready()` with a loop that keeps stepping and laying rows until there are enough. The first `lay_row()` stays where it was and lays row 0, the seed. Then add `step()`:

```gdscript
	while made < rows:
		step()
		lay_row()

func step() -> void:
	for i in n:
		var index := now[(i - 1 + n) % n] * 4 + now[i] * 2 + now[(i + 1) % n]
		now[i] = (rule >> index) & 1
```

A **step** makes every cell's next state from the last state. For each cell `i`, the loop reads its left neighbour, itself and its right neighbour, builds the index and writes the answer back into `now[i]`. (The `% n` in the neighbour indices keeps them inside the row at the two ends. Section 13.5 explains it.)

**Predict row 1 before you press Play.** Row 0 has only cell 8 live. Cell 7 sees the neighbourhood 001, so the answer is 1. Cell 8 sees 010, so the answer is 0. Cell 9 sees 100, so the answer is 1. Every other cell sees 000, so the answer is 0. Row 1 should therefore be two live cells with a gap between them where the seed was. And because Rule 90 answers each neighbourhood the same way as its mirror image (110 and 011 both give 1, and 100 and 001 both give 1), the whole floor should come out mirrored, the same on the left as on the right.

Now press Play. Row 1 is **ten** cells, and the floor leans to the right.

There is no error message. The code ran exactly as written, so the mistake is in what was written. `step()` writes row 1 into `now` while it is still reading row 0 from `now`. The loop runs from left to right:

- Cell 7 reads 0, 0, 1, the old values. It becomes 1. That is correct.
- Cell 8 reads its left neighbour, cell 7. But cell 7 is **already new**: it is now 1 instead of 0. So cell 8 sees 110 instead of 010 and becomes 1.
- Cell 9 reads cell 8, also already new, sees 100 and becomes 1.
- And so on to the end of the row.

[worked by hand] Row 1 comes out as cells 7 through 16, which is ten cells. The mistake runs to the right because the loop runs to the right: each wrong answer becomes the left neighbour of the next cell's question.

## 13.4 Two buffers

*Picture: the repaired stair, a triangle of triangular holes.*

The fix is a second buffer. Add a variable `next` and resize it like `now`:

```gdscript
var next := PackedByteArray()
```

and in `_ready()`, beside `now.resize(n)`:

```gdscript
	next.resize(n)
```

Then replace `step()`:

```gdscript
func step() -> void:
	for i in n:
		var index := now[(i - 1 + n) % n] * 4 + now[i] * 2 + now[(i + 1) % n]
		next[i] = (rule >> index) & 1
	var spare := now
	now = next
	next = spare
```

The loop reads only from `now` and writes only into `next`. **Questions go to the old row, answers to the new.**

> "An answer written at the left cannot slip into the question being asked at the right."

When the loop has finished, `next` holds the whole new row. The last three lines **swap** the two names: `now` becomes the new row, which the next `lay_row()` draws, and `next` becomes the old row, whose bytes the next step will simply overwrite. The swap trades names. No byte is copied or moved: three assignments, whatever the size of the row.

Press Play again. Row 1 is two cells. The floor is **Sierpinski's triangle**, a triangle made of triangular holes, with holes inside the holes.

row 3  .....#.#.#.#.....
row 4  ....#.......#....
row 5  ...#.#.....#.#...
row 6  ..#...#...#...#..
row 7  .#.#.#.#.#.#.#.#.

## 13.5 The ring

*Picture: row 9, with a live cell at each end.*

Look at row 9. Cell 0 is alive, and it is alive because cell 16, at the other end of the row, was alive in row 8. How can a cell at one end hear about a cell at the other?

Because of `(i - 1 + n) % n`. For cell 0 the left neighbour would be cell −1, which does not exist. Adding `n` makes it 16, and `% n` leaves 16. For cell 16 the right neighbour `(16 + 1) % 17` is 0. The index **wraps**: the row behaves as a **ring**, with its two ends touching.

A real row has to end somewhere, and a ring is only one way to end it. So make the ending a choice. Add an export:

```gdscript
@export var ring := true
```

and read every neighbour through this function:

```gdscript
func cell_at(i: int) -> int:
	if ring:
		return now[(i + n) % n]
	if i < 0 or i >= n:
		return 0
	return now[i]
```

With `ring` true, an index just outside the row wraps round to the other end. With `ring` false, anything beyond an end counts as dead: a **dead end**.

[guess] The loop in `step()` then reads its neighbourhood through `cell_at()` instead of indexing `now` directly:

```gdscript
		var index := cell_at(i - 1) * 4 + cell_at(i) * 2 + cell_at(i + 1)
		next[i] = (rule >> index) & 1
```

The two endings make different floors, but only at the border. [worked by hand] For Rule 90 with 17 cells and 11 rows, nothing reaches the ends until row 8 ({0, 16} under both endings). After that, row 9 differs in 2 cells (the ring has 0, 1, 15, 16, the dead end only 1, 15) and row 10 in 4 cells (ring 1, 2, 14, 15, dead end 0, 2, 14, 16). That is 6 cells of 187 in all.

## 13.6 A stair to stand on

*Picture: the walker standing on the seed, stopped before the gap in row 1.*

So far all the rows appear at once. Make them grow one at a time. Add:

```gdscript
@export var pace := 0.25    # seconds between rows
var clock := 0.0
```

`_ready()` should run its `while` loop only when `pace` is 0, which means "build everything at once". Otherwise `_process` lays the remaining rows one by one. [guess] The end of `_ready()` becomes:

```gdscript
	lay_row()
	if pace <= 0.0:
		while made < rows:
			step()
			lay_row()
```

and `_process` is:

```gdscript
func _process(delta: float) -> void:
	if pace <= 0.0 or made >= rows:
		return
	clock += delta
	if clock >= pace:
		clock -= pace
		step()
		lay_row()
```

Each frame adds the time since the last frame (`delta`) to `clock`. When `pace` seconds have built up, one step and one row are made. Subtracting `pace`, rather than setting `clock` back to 0, keeps any leftover time, so the rows keep an even beat.

Now raise each row by `made * rise` as well as moving it back by `made * cell`. Depth and height both stand for time: the oldest row is lowest and in front, the newest is highest and furthest back. **The history is a stair.**

But the walker walks straight through it. A `MultiMesh` is only something to look at; it has no collision. To be stood on, each row needs a body. Make the row a `StaticBody3D` and give it one collision box for each **stretch**, a run of live cells with no gap in it:

```gdscript
func lay_row() -> void:
	var row := StaticBody3D.new()
	row.position = Vector3(0.0, made * rise, -made * cell)
	add_child(row)
	var tiles := MultiMesh.new()
	tiles.transform_format = MultiMesh.TRANSFORM_3D
	tiles.mesh = tile
	tiles.instance_count = now.count(1)
	var drawn := MultiMeshInstance3D.new()
	drawn.multimesh = tiles
	row.add_child(drawn)
	var k := 0          # which tile comes next
	var start := -1     # where this stretch of live cells began; -1: none yet
	for i in n + 1:
		if i < n and now[i] == 1:
			tiles.set_instance_transform(k, Transform3D(Basis(), Vector3(x_of(i), rise / 2.0, 0.0)))
			k += 1
			if start < 0:
				start = i
		elif start >= 0:
			var box := BoxShape3D.new()
			box.size = Vector3((i - start) * cell, rise, cell)
			var touch := CollisionShape3D.new()
			touch.shape = box
			touch.position = Vector3((x_of(start) + x_of(i - 1)) / 2.0, rise / 2.0, 0.0)
			row.add_child(touch)
			start = -1
	print(made, " ", now)
	made += 1
```

How the stretch finder works:

- `start` remembers where the current stretch of live cells began. −1 means "not in a stretch".
- At a live cell: place its tile as before, and if no stretch is open, open one here.
- At a dead cell while a stretch is open: the stretch has just ended at cell `i - 1`. Make a `BoxShape3D` as wide as the stretch, `(i - start) * cell`, as thick as a tile and one cell deep. Centre it halfway between the first and last cells of the stretch, and put it in a `CollisionShape3D` on the row. Then close the stretch.
- **Why `n + 1`?** The loop runs one step past the last cell, to `i == n`. There `i < n` is false, so the code falls into the `elif`. If a stretch is still open, because it runs right up to cell 16, this extra step closes it. Without that step, the last stretch in a row whose final cell is live would never get its box, and that part of the floor would be visible but not solid.

[worked by hand] For Rule 90 with the ring, the eleven rows hold 1, 2, 2, 4, 2, 4, 4, 8, 2, 4 and 4 live cells: **37 tiles**. They make 1, 2, 2, 4, 2, 4, 4, 8, 2, 2 and 2 stretches: **33 boxes**. Only rows 9 and 10 have stretches longer than one cell. (With the dead end it would be 35 tiles and 35 boxes.)

Press Play. The walker steps onto the seed and then stops. Row 1's gap, the empty cell where the seed was, is 0.4 m wide, and the walker is 0.6 m wide. [guess] The walker walks straight ahead up the middle, and directly ahead of it in row 1 there is no tile. Being wider than the gap keeps it from falling into the hole, but with nothing under its centre it does not step forward.

**Stop here** and check: the rows rise one by one, row 1 is two cells, and the walker stands on the seed.

## 13.7 Which rule?

*Picture: the sheet, the four floors (30, 90, 110, 250) each shown from above and from in front.*

To try another rule, change `rule`, either in the Inspector or in the script, **but not both**. Once you have set a value in the Inspector, the scene saves it, and the saved value wins over the default written in the script. It does so without any warning, so a change to the script appears to do nothing.

**Predict:** which two floors look most alike? A clue: 90 and 250 differ in two of their eight answers, and so do 30 and 90.

[worked by hand] To compare answers, write the rules in binary: 30 is 00011110, 90 is 01011010, 110 is 01101110 and 250 is 11111010. Counting the places where two of them differ gives the middle column of the table below. The last column counts how many cells, out of all 17 × 11 = 187 cells on the floor, are different.

| pair | answers that differ | cells that differ, of 187 |
| --- | --- | --- |
| 30, 90 | 2 | 46 |
| 30, 110 | 3 | 56 |
| 30, 250 | 4 | 49 |
| 90, 110 | 3 | 58 |
| 90, 250 | 2 | 29 |
| 110, 250 | 3 | 59 |

Both 30/90 and 90/250 differ in two answers, but they are not equally alike. 90 and 250 differ in only 29 cells, the fewest of any pair, while 30 and 90 differ in 46. 90 and 250 are closest because Rule 250's floor is a checker, which is Sierpinski's triangle with its holes filled in. [worked by hand] Rule 250 lights a cell whenever its left or right neighbour is live. Rule 90 lights it when exactly one of them is. So 250 fills in the cells inside the triangle that 90 leaves empty, alternating live and dead like a chessboard.

Rule 110 leans by weight and Rule 30 by arrangement. [guess] Rule 110 grows only to one side, so its mass of live cells piles up on the left. Rule 30 spreads to both sides, but its pattern is lopsided inside: orderly on one side, disordered on the other.

The conclusion: **how far apart two rules' answers are does not tell you how far apart their floors are.** Eight bits choose between a checker, a triangle, a lean or disorder, and the bits do not say which. The only way to find out is to run them.

Now go back to the question from section 13.1: which floor would you least like to cross on foot? **The body measures otherwise than the eye.** By eye, from the table, 90 and 250 are near twins. A body tests something else, namely whether there is support where it puts its weight.

- A marble falls through Rule 90 but rests on 250. [guess] The marble is a small ball dropped onto the floor; 90's holes are big enough for it, while 250's checker leaves it nowhere to fall through.
- Walking up the middle, the walker climbs Rule 110 all the way to the top, because 110's middle cell always lives: there is a tile on the centre line in every row.
- It falls through Rule 30. [worked by hand] Rule 30's row 1 is three cells, so the walker gets onto it, but row 2 has a hole in the middle. On 90 and 250 it stops on the seed, as you saw in 13.6.

So the eye's pair of twins, 90 and 250, comes apart for the marble, while for the walker they are the same: it stops on the seed of both. And Rule 110, a lean the eye might distrust, is the only one the walker can climb.

## 13.8 The same step, another rule

*Picture: the pool, an orange block hollowing out into a square wall.*

Open `diffusion.tscn`. Here a cell holds not one bit but two amounts, called A and B. B is made from A; both amounts spread to the neighbouring cells; A is fed in from outside and B is taken out. This is called **reaction-diffusion**.

The supplied part of `diffusion.gd` (its `_ready()` and `show_b()`) draws B and hands B's heights to a collision shape. [guess] The supplied `_ready()` also creates the grid size `g`, the four buffers `a`, `b`, `a_next` and `b_next` (each a `PackedFloat32Array` of `g * g` floats, one per cell of a square grid), the values `feed` and `kill` (supplied as 0.055 and 0.062, values from Gray and Scott), and the counter `steps`. You write the step:

```gdscript
func around(buffer: PackedFloat32Array, x: int, z: int) -> float:
	var left := buffer[z * g + (x - 1 + g) % g]
	var right := buffer[z * g + (x + 1) % g]
	var back := buffer[(z - 1 + g) % g * g + x]
	var front := buffer[(z + 1) % g * g + x]
	return (left + right + back + front) / 4.0

func step() -> void:
	for z in g:
		for x in g:
			var i := z * g + x
			var eaten := a[i] * b[i] * b[i]
			a_next[i] = a[i] + 0.32 * (around(a, x, z) - a[i]) - eaten + feed * (1.0 - a[i])
			b_next[i] = b[i] + 0.16 * (around(b, x, z) - b[i]) + eaten - (feed + kill) * b[i]
	var spare := a
	a = a_next
	a_next = spare
	spare = b
	b = b_next
	b_next = spare
	steps += 1
```

**The grid is flat in memory.** The square grid is stored as one long array, row after row, so cell (x, z) sits at index `z * g + x`.

**`around()` is the neighbourhood.** In the stair, a cell's neighbourhood was left and right. Here it is the four cells left, right, behind and in front. `around()` returns their mean. The `% g` wraps every index exactly as `% n` did in the ring, so the grid's edges join up left to right and front to back.

**The step, line by line:**

- `eaten = a * b * b` is the reaction: where there is B, A is turned into more B. The more B there is, the faster it happens.
- `0.32 * (around(a) - a)` is spreading: each cell moves part of the way towards the average of its neighbours. A spreads at 0.32 and B at 0.16, so A spreads twice as fast.
- `- eaten` takes the converted A away; `+ eaten` adds it to B.
- `feed * (1.0 - a)` feeds A in, topping it up towards 1.
- `(feed + kill) * b` takes B out.

**It is the stair's step, twice.** Read from `a` and `b`, write into `a_next` and `b_next`, then swap both pairs of names. Two buffers for A and two for B, for the same reason as before: no cell may read a neighbour's answer before it has asked its own question.

Press Play. The block hollows out into a wall: this is the **pool**. A walker standing on it is first lifted, then lowered, and ends up walled in.

## 13.9 What the floor owes

*Picture: the ring and the dead end side by side, with the border cells that differ marked.*

Some honesty about what was built.

**The ends.** The rule is defined on a row without ends, an endless row. No machine has an endless row. Every stair you build had to choose an ending, ring or dead end, and that choice shows at the border.

**The chance.** Rule 30 looks random, but there is no chance in it. Its first row is a seed, and the seed together with the rule fixes every later row, every "draw", in advance. [guess] This is the same lesson as the seed in the randomness chapter: a seeded random generator looks random but repeats exactly from the same seed.

**The name.** The pool follows Gray and Scott's scheme. It is not Turing's equations of 1952, although Turing first proposed reaction-diffusion as an explanation for the spots on living things.

> "Pattern formation alone has not made a solid that can bear your weight."

The pool bears weight only because of choices. One line of code hands B to a shape, and a tenth, 0.1, is the threshold for what counts as solid. [guess] Wherever B is above 0.1 there is something to stand on; below it there is nothing.

[guess] *Can twisted rooms transcend power?* The lesson leaves this as an open question, and so do I. The point it presses is that a pattern that "forms itself" does not take the author out of the picture. **The author still chose the ends, the seed, and what counts as there.**

## 13.10 In your room

*Picture: your room, with a small stair at place 2 and the walker standing on it.*

A **recipe** is the list of operations that made a body. The **process strip** shows one still picture per operation. For this chapter the strip runs:

## Appendix: the finished `cellular.gd`, assembled

[guess] Assembled from the sections above. The compressed lesson never prints the whole script, so the order of declarations and the exact `_ready()` guard are my reconstruction.

```gdscript
extends Node3D

const Look := preload("res://supplied/look.gd")

@export var n := 17                    # cells in a row
@export var cell := 0.4                # metres: a cell's width and depth
@export var rise := 0.15               # metres: tile thickness and per-row climb
@export_range(0, 255) var rule := 90
@export var rows := 11
@export var ring := true
@export var pace := 0.25               # seconds per row; 0 builds all at once

var now := PackedByteArray()
var next := PackedByteArray()
var tile := BoxMesh.new()
var made := 0
var clock := 0.0

func _ready() -> void:
	tile.size = Vector3(cell * 0.9, rise, cell * 0.9)
	tile.material = Look.paint(Look.BODY)
	now.resize(n)
	next.resize(n)
	@warning_ignore("integer_division")
	now[n / 2] = 1
	lay_row()
	if pace <= 0.0:
		while made < rows:
			step()
			lay_row()

func _process(delta: float) -> void:
	if pace <= 0.0 or made >= rows:
		return
	clock += delta
	if clock >= pace:
		clock -= pace
		step()
		lay_row()

func step() -> void:
	for i in n:
		var index := cell_at(i - 1) * 4 + cell_at(i) * 2 + cell_at(i + 1)
		next[i] = (rule >> index) & 1
	var spare := now
	now = next
	next = spare

func cell_at(i: int) -> int:
	if ring:
		return now[(i + n) % n]
	if i < 0 or i >= n:
		return 0
	return now[i]

func lay_row() -> void:
	var row := StaticBody3D.new()
	row.position = Vector3(0.0, made * rise, -made * cell)
	add_child(row)
	var tiles := MultiMesh.new()
	tiles.transform_format = MultiMesh.TRANSFORM_3D
	tiles.mesh = tile
	tiles.instance_count = now.count(1)
	var drawn := MultiMeshInstance3D.new()
	drawn.multimesh = tiles
	row.add_child(drawn)
	var k := 0
	var start := -1
	for i in n + 1:
		if i < n and now[i] == 1:
			tiles.set_instance_transform(k, Transform3D(Basis(), Vector3(x_of(i), rise / 2.0, 0.0)))
			k += 1
			if start < 0:
				start = i
		elif start >= 0:
			var box := BoxShape3D.new()
			box.size = Vector3((i - start) * cell, rise, cell)
			var touch := CollisionShape3D.new()
			touch.shape = box
			touch.position = Vector3((x_of(start) + x_of(i - 1)) / 2.0, rise / 2.0, 0.0)
			row.add_child(touch)
			start = -1
	print(made, " ", now)
	made += 1

func x_of(i: int) -> float:
	return (i - (n - 1) / 2.0) * cell
```
