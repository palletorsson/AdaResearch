*Picture: the stair. Rows of lime tiles, each row a little higher and a little further back than the one before it. Seen from the front, the holes make Sierpinski's triangle.*

In this chapter you build a body that is a **history**. You start with one row of cells. A **rule** turns that row into the next row. You keep every row, and each new row goes one step higher than the last. When you are done you have a stair: the past is the bottom step, the present is the top step, and you can walk on it.

The one new programming idea is **two buffers**. By the end you will know why one buffer is not enough.

## 13.2 One row

*Needs: arrays, `PackedByteArray`, `MultiMesh`, a seed. Gives: cell, row, buffer, tile.*

*Picture: one lime tile, and a list of seventeen numbers with exactly one of them set to 1.*

A **cell** is either dead (0) or live (1). A **row** is cells side by side. A **buffer** is an array that holds one row. We store the row in a `PackedByteArray`, which is a compact array of bytes, because a cell is only ever 0 or 1.

```gdscript
var n := 17                       # [guess] the row is 17 cells wide (the picture shows seventeen numbers)
var now := PackedByteArray()

func _ready() -> void:
	now.resize(n)                         # a buffer: one row of n cells, all 0
	now[n / 2] = 1                        # the seed
	tiles.instance_count = now.count(1)   # one tile per live cell
```

- `resize(n)` makes the array `n` long and fills it with 0. Every cell starts dead.
- `now[n / 2] = 1` sets the middle cell live. That single live cell is the **seed**. With `n = 17`, the seed is cell 8.
- `count(1)` counts how many cells are live. You need that many **tiles**. A tile is the lime box that shows a live cell, and you draw the tiles with a `MultiMesh`, one instance per live cell.

**[guess]** After you set `instance_count`, you go through the row and give each live cell's instance a transform with `tiles.set_instance_transform(...)`, placed at x = `(i - n / 2) * cell`.

Keep two things apart from the start. **A buffer is bytes, nothing else.** It does not know where anything is or what anything looks like. **A tile is only something you see.** Nothing in the buffer depends on it, and as you will find in 13.6, nothing can stand on it either.

## 13.3 The rule

*Needs: cell, buffer, `%`. Gives: neighbourhood, bit, rule, step.*

*Picture: Rule 90's table of eight answers, and a floor that leans to the right.*

### Neighbourhood

To decide what a cell becomes, an elementary cellular automaton looks at three cells: the one on the **left**, the cell **itself**, and the one on the **right**. That is the **neighbourhood**. Each of the three is a **bit** (0 or 1), so together they spell a three-bit binary number from 0 to 7. That makes 8 possible cases:

| left self right | 111 | 110 | 101 | 100 | 011 | 010 | 001 | 000 |
|---|---|---|---|---|---|---|---|---|
| case (index) | 7 | 6 | 5 | 4 | 3 | 2 | 1 | 0 |
| Rule 90's answer | 0 | 1 | 0 | 1 | 1 | 0 | 1 | 0 |

### The rule is its own name

A **rule** gives one answer (a bit) for each of the 8 cases, so a rule is 8 bits. Read the bottom row of the table from left to right as a binary number: `01011010`. In decimal that is 64 + 16 + 8 + 2 = **90**. That is where the name comes from: the rule's number *is* its table of answers. Every rule from 0 to 255 is named this way.

(Reading the table: Rule 90 makes a cell live exactly when one of its two neighbours is live, whatever the cell itself was. In other words, new = left XOR right.)

### Reading one answer out of the number

Turn the neighbourhood into its case number, then pull that bit out of `rule`:

```gdscript
var index := now[(i - 1 + n) % n] * 4 + now[i] * 2 + now[(i + 1) % n]
now[i] = (rule >> index) & 1   # written where it is read
```

- `left * 4 + self * 2 + right` builds the three-bit number 0 to 7.
- `(i - 1 + n) % n` and `(i + 1) % n` keep the index inside the row. Cell 0's left neighbour becomes cell `n - 1`, and the last cell's right neighbour becomes cell 0. (Section 13.5 comes back to this choice.)
- `rule >> index` shifts the rule right by `index` places, so the answer you want ends up in the lowest bit. `& 1` keeps only that bit.

Running this for every `i` from 0 to `n - 1` is one **step**: all the next states, computed from the last ones.

### Predict, then run

Predict row 1 before you run it. The seed (cell 8) sees left 0, self 1, right 0, which is case 2, and the answer for case 2 is 0, so the seed dies. Cells 7 and 9 each see exactly one live neighbour (cases 1 and 4), both answer 1. Every other cell sees nothing. **Prediction: row 1 has two live cells, mirrored about the seed.**

What you actually get: **ten live cells, leaning right. No error message.**

### Why

This step **writes where it reads**. The loop goes left to right and overwrites `now[i]` straight away. When the loop reaches cell `i + 1`, its left neighbour `now[i]` already holds the *new* value, not the old one.

Follow it through. Cells 0 to 6 stay 0. Cell 7 becomes 1, which is correct. At cell 8, the left neighbour (cell 7) now reads 1 and the right reads 0, so cell 8 becomes 1, which is wrong because the seed should have died. At cell 9 the left neighbour is now 1, so it becomes 1. The same thing happens at 10, 11, and so on up to cell 16. That is cells 7 to 16: ten cells. Each new cell becomes the next cell's left neighbour, so **the error runs the same way the loop runs**, and the floor leans to the right. Nothing crashes because nothing is illegal. The program just answers a different question from the one you meant to ask.

## 13.4 Two buffers

*Needs: step, buffer. Gives: two buffers, swap, Sierpinski.*

*Picture: the repaired floor, Sierpinski's triangle.*

The fix is to keep the questions and the answers apart. You **read** the neighbourhood from the old row (`now`) and **write** the answer into a second row (`next`):

```gdscript
var next := PackedByteArray()   # [guess] resized to n in _ready(), like now: next.resize(n)

func step() -> void:
	for i in n:
		var index := now[(i - 1 + n) % n] * 4 + now[i] * 2 + now[(i + 1) % n]
		next[i] = (rule >> index) & 1
	# after the loop, the swap:
	var spare := now
	now = next
	next = spare
```

The questions go to the old row and the answers go to the new row: "An answer written at the left cannot slip into the question being asked at the right."

The three lines after the loop are the **swap**. The new row becomes `now`, ready for the next step to read. The old row becomes `next`, ready to be overwritten. Only the names trade places: **no byte moves**. You are not copying 17 cells, you are relabelling two buffers.

Now row 1 has two cells, as predicted, and the whole floor is **Sierpinski's triangle**: a triangle of holes inside holes.

## 13.5 The ring

*Needs: `%`, wrap. Gives: ring, dead end.*

*Picture: row 9, live at both ends.*

A row has to end somewhere, and the rule does not say what lies past the end. You have to choose:

- **Ring**: the two ends are neighbours, as if the row were bent into a loop. This is what the `%` in 13.3 already does.
- **Dead end**: everything beyond the row counts as dead.

Put the choice in one function that the step asks for neighbours:

```gdscript
@export var ring := true   # [guess] exported so you can flip it

func cell_at(i: int) -> int:   # [guess] the name and signature; the compressed text shows only the body
	if ring:
		return now[(i + n) % n]
	if i < 0 or i >= n:
		return 0
	return now[i]   # [guess] the in-range line, implied but not shown
```

**[guess]** The index line in `step()` then becomes `var index := cell_at(i - 1) * 4 + cell_at(i) * 2 + cell_at(i + 1)`.

The two choices **differ only at the border**. For Rule 90 the pattern widens by one cell each row, so it first reaches the ends at row 8. From row 9 on, the ring lets each end see the other: ring row 9 is live at cells 0, 1, 15 and 16, while dead-end row 9 is live only at 1 and 15. Computed over the whole floor of 11 rows × 17 cells = 187 cells, the ring floor and the dead-end floor differ in **6 cells**, all in rows 9 and 10.

## 13.6 The stair

*Needs: frame, `delta`, body, shape, walker. Gives: stair, stretch.*

*Picture: the walker standing on the seed, stopped at the gap in row 1.*

Now the rows rise. Every frame you add `delta` (the seconds since the last frame) to a clock. Whenever the clock passes `pace`, you take one step and lay one new row:

```gdscript
@export var pace := 0.5   # [guess] seconds per row; the value is not given
var clock := 0.0

func _process(delta: float) -> void:
	clock += delta
	if clock >= pace:
		clock -= pace
		step()
		lay_row()
```

Subtracting `pace` instead of setting the clock back to 0 keeps any leftover time, so the rhythm does not drift.

In `lay_row()`, row number `k` goes at position `(0, k * rise, -k * cell)`: `rise` higher and one `cell` further back for each row. **Depth and height are time.** The history becomes a stair.

### Why the tiles are not enough

A `MultiMesh` is **for the eye only**. It has no collision, so the walker walks straight through the tiles. To make a row something you can stand on, each row has to become a `StaticBody3D` with collision shapes.

Rather than one box per live cell, you make one box per **stretch**: a run of live cells with no gap between them.

```gdscript
var k := 0                                                # [guess] the number of the next row to lay

func lay_row() -> void:
	var body := StaticBody3D.new()                        # [guess] one body per row
	body.position = Vector3(0, k * rise, -k * cell)       # k = this row's number
	var start := -1
	for i in n + 1:                                       # one past the end, see below
		var live := i < n and now[i] == 1
		if live and start < 0:
			start = i                                     # a stretch begins
		elif not live and start >= 0:
			var box := BoxShape3D.new()
			box.size = Vector3((i - start) * cell, rise, cell)   # one box per stretch
			var shape := CollisionShape3D.new()           # [guess] the wiring around the box
			shape.shape = box
			shape.position.x = ((start + i) / 2.0 - n / 2.0) * cell   # [guess] centre of the stretch
			body.add_child(shape)
			start = -1                                    # the stretch ends
	add_child(body)
	k += 1
```

**[guess]** The loop runs to `n + 1` so that the step after the last cell counts as dead. A stretch that reaches the end of the row then gets closed and receives its box. If the loop stopped at `n`, the last stretch would never be written.

The box is `(i - start)` cells wide, one `rise` high and one `cell` deep.

Computed, for Rule 90 with the ring, 11 rows of 17 cells: **37 tiles and 33 boxes**. (With a dead end it is 35 tiles and 35 boxes.)

### The walker

Put the walker on the seed. **[guess]** It walks straight forward up the middle of the stair, and with `cell` = 0.4 m, row 1's gap is 0.4 m wide. The walker is 0.6 m, wider than the gap, so it does not drop into it. But in Rule 90 the middle cell of row 1 is dead, so there is no step in front of it. **It stands on the seed and stops.**

**Stop here.** You have the stair. Keep the question of the walker for the next section.

## 13.7 Which rule

*Needs: family, Sierpinski, body. Gives: nothing new to learn, only things to decide.*

*Picture: the four floors, seen from above and from the front.*

### Setting the rule

To change the floor, set `rule` either in the Inspector or in the script, **not both**. A value saved in the scene overrides the default written in the script, and it does so **silently**. You edit the script, nothing changes, and nothing tells you why.

### How alike are the rules?

Count how many of the 8 answers two rules disagree on, then count how many of the 187 cells their floors disagree on:

| pair | answers apart | cells apart (of 187) |
|---|---|---|
| 90 · 250 | 2 | 29 (closest) |
| 30 · 90 | 2 | 46 |
| 30 · 250 | 4 | 49 |

Rules 90 and 250 are 2 answers apart, and so are 30 and 90, but their floors are not equally far apart: 29 cells against 46. **Answers apart does not mean floors apart.** The 8 bits decide whether you get a checker, a triangle, a lean or disorder, and nothing in the bits tells you which. You have to **run them**. **[guess]** Matching the pictures: 250 gives the checker, 90 the triangle, 110 the lean, 30 the disorder.

### The eye is not the body

Go back to the question you answered at the start. The eye judges a floor by its pattern. A body judges it by whether there is support where it puts its weight, and that depends on the body's size compared with the gaps:

- **A marble** falls through Rule 90's holes but rests on Rule 250.
- **The walker** climbs to the top of Rule 110, because 110's middle cell stays live. It falls into Rule 30. It stops on the seed of both 90 and 250.

So the floor that looks most orderly (90's triangle) is not the one that carries a body, and the disordered one (30) is the one you fall into.

**Decide**: either make `cell` 0.2 m, or pick one of the four floors as it is. Write down why. **[guess]** With 0.2 m cells the walker spans three cells instead of one and a half, so single-cell gaps no longer stop it. The question is whether you change the body or the floor to make them fit.

## 13.8 The pool

*Needs: step, neighbourhood, swap, wrap, shape. Gives: reaction-diffusion, pool.*

*Picture: an orange block that goes hollow, then becomes a square wall.*

The same machinery runs a continuous automaton. Each cell now holds two amounts, A and B, as floats in a 2D grid. **[guess]** They are stored in `PackedFloat32Array`s of size width × depth, with `a`, `b`, `a_next`, `b_next`. This is **reaction-diffusion**: two amounts that spread out and react with each other.

- **B eats A.** Where they meet, A turns into B.
- **Both spread** to their neighbours, B **half as fast** as A (0.16 against 0.32).
- **A is fed**: it is topped up towards 1. **B is killed**: it drains away.

```gdscript
var eaten := a[i] * b[i] * b[i]   # [guess] the usual Gray-Scott reaction term; not given
a_next[i] = a[i] + 0.32 * (around(a, x, z) - a[i]) - eaten + feed * (1.0 - a[i])
b_next[i] = b[i] + 0.16 * (around(b, x, z) - b[i]) + eaten - (feed + kill) * b[i]
```

`around(grid, x, z)` returns the **mean of the 4 neighbours** of cell (x, z): left, right, front and back, **wrapped** like the ring, so the edges meet. `around(...) - a[i]` is how far the cell is from its neighbours' average, and the 0.32 or 0.16 decides how quickly it closes that difference.

**[guess]** A sketch of `around()`:

```gdscript
func around(g: PackedFloat32Array, x: int, z: int) -> float:
	var l := g[((x - 1 + w) % w) + z * w]
	var r := g[((x + 1) % w) + z * w]
	var f := g[x + ((z - 1 + d) % d) * w]
	var bk := g[x + ((z + 1) % d) * w]
	return (l + r + f + bk) / 4.0
```

It is **the same step as the stair's, done twice** (once for A, once for B), with **the same swap**. Read from the old grids, write into the new ones, then trade names.

The **pool** shows B's amounts as tiles of different heights. `show_b()` in `diffusion.gd` is supplied and draws that. The default `feed` and `kill` are supplied too, 0.055 and 0.062 (**[guess]** in that order). Starting from a block of B, the pool goes hollow and grows into a square wall. Once the pool has collision, it **lifts the walker standing on it, then walls it in.**

## 13.9 What is owed

*Needs: ring, dead end, seed, random, pool, threshold. Gives: Turing, Gray-Scott.*

*Picture: the ring and the dead end side by side, with the border marked.*

Some honest accounting.

- **The ends.** The rule assumes a row with no ends. No machine has one. Every floor you built carries a choice, ring or dead end, that the rule itself never made.
- **Rule 30 looks random but holds no chance.** Once the first row (the seed) is fixed, every later "draw" is fixed too. Run it again and you get exactly the same floor. **[guess]** This links back to the randomness chapter: a pseudo-random sequence is fixed by its seed in the same way.
- **The pool is Gray-Scott, not Turing.** Turing's 1952 paper showed spots arising from reaction. The scheme you coded is the later Gray-Scott model. Do not credit Turing with this pool.
- **Pattern alone bears no weight.** That was the hall's point. What makes the pool a floor you can stand on is **your line** that turns B into a shape (collision), plus **your threshold**: B above 0.1 counts as solid. Both are your decisions, not the pattern's.
- An open question the lesson leaves: *can twisted rooms transcend power?* (The compressed text gives no context for this. I am keeping it as an open question.)

**You chose the ends, the seed, and what counts as being there.** Those choices are yours, not the automaton's.

## 13.10 Your room

*Needs: rule, body, shape. Gives: recipe, process strip, guest.*

*Picture: your room, with the small stair standing at place 2.*

### The recipe

The **recipe** is the operations in order:

**row → rule → two buffers → rising → shapes → walker → diffusing**

The **process strip** is one still image per operation. Notice one thing about it: **the shapes step changes the body but not the strip**. Adding `StaticBody3D`s and boxes makes the stair solid, but its still looks exactly like the one before it. **[guess]** So the strip cannot show the fault that the walker passed through the tiles, or its fix. Only a body walking on the stair shows that.

### The guest

Your stair goes into your room as a **guest**: a body built from its own folder.

1. Put it in `guests/cellular/`.
2. Add it to `GUESTS` (**[guess]** the list of guests the room loads).
3. Set your rule.
4. Write a README saying **what it grows and what it leaves out**.

**[guess]** A guest's script should only use what is in its own folder, so it can be dropped into any room.

### Carry forward

- **Two buffers**: read one, write one, swap.
- **A rule is a number**: its 8 answers, read as binary.
- **`%` makes a ring.**
- **A body is a record of how it was made.**

And the habit: **when a floor leans, ask which row the rule read.** It comes from the one-buffer fault in 13.3.
