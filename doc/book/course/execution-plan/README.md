## Editorial decision

Keep the museum order for now. Use a small operation before its deeper study when that operation enables the current work. A bounded sine expression can help move a body in Transformation; Waves later owns its circular construction. A bounded random draw can enable Annealing; Randomness later owns generators, draw order, distributions and sampling policy.

The inventory is a coverage reference. It is not a command to reproduce a Processing course inside Godot. Godot's `Array` already grows dynamically; we do not need a separate Java `ArrayList` lesson. Three dimensions and the prepared camera belong to the opening world. There is no reason to postpone them until the inventory's final item.

The official [Nature of Code introduction](https://natureofcode.com/introduction/#what-do-you-need-to-know) assumes variables, conditions, loops, functions, objects and arrays. Ada's opening sequences should make these usable before the later simulations. Seeing syntax once does not establish that capacity.

## Additional thinking worth teaching

These are recurring distinctions within existing lessons, not ten additional chapters.

| Concern | First useful situation | What it prevents |
| --- | --- | --- |
| Pickup/release and grip alignment | Coordinates, returning in Trace | Treating a mesh as if it already had interaction behaviour. |
| Named actions, events and states | Transformation, returning in Paint | Unexplained controller-specific branches and duplicated behaviour. |
| Targeting, snapping and feedback | Grid, Arena, Paint | Confusing an apparent target, a valid action and its recorded result. |
| Identity, resources and ownership | Lines, Arrays, Palette | Accidentally changing all copies through one shared resource. |
| Units and reference frames | Coordinates, Grid, Pillar | Combining positions from incompatible frames or rates with the wrong units. |
| Code, data and lifetime | Trace → Grid | Claiming an array survives a scene change because its code exists in two tutorials. |
| Function contracts and invalid inputs | Generators, Colour, surface extraction | Supplying a plausible expression without its domain or promised result. |
| Observation and tests | From Point Zero onward | Confusing a running program, a passing assertion and a student's understanding. |
| Snapshot/update separation | CA, later swarms | An unintended dependence on traversal order. |
| Model, implementation, display and claim | Point One through Foundations Crisis | Treating a visual metaphor, a numerical result and a mathematical proof as interchangeable. |

This is the practical use of the project's “type-safe” writing: connections remain possible because their terms are stated. A point value, a sphere mesh, a collider, an inherited pickup behaviour and a critical interpretation can meet without pretending to be the same object.

## Deliberate gaps and optional branches

- **Particle lifecycle/emitter code:** the spray feedback supplies a relevant encounter; it does not mean the student already owns particle creation, updates and expiry. A later population mini-study is a candidate requiring source inspection.
- **Seek/flee/arrive/wander:** one agent can prepare the Boids hall. Add variants selectively after the current source and teaching load are checked. Pursuit/evade remain unplaced.
- **Elementary CA and Life:** inspect actual state/rule implementations. The current curated description of `CA_ElementaryRules` is a three-state neighbour-count system; the hall name alone cannot justify a binary rule-bit tutorial.
- **Training:** numerical descent in Form Finding prepares optimization, but model training belongs with data, predictions and loss in Machine Learning. Centroid clustering is not a perceptron lesson.
- **Neuroevolution:** requires both genetic representation and a network evaluator; a later return is more honest than a forward prerequisite.
- **Voronoi, Delaunay and DLA:** deliberately unplaced. Space colonization is not DLA. Add a branch only when an encounter needs the operation.
- **FFT and complex physics engines:** possible later extensions. A score/synthesis lesson or a supplied solver does not establish mastery of them.

## Contract for a writing pass

### Recognizable objects carry the learning

Author clarification, 5 October: continuity includes **the object's look**, not only its code or data. Reuse a small family of learner-made objects so a new lesson can concentrate on the changed operation. The sphere introduced in Point One returns through Coordinates, Lines and Trace, then can become the moving body in Forces. The cube constructed from vertices and faces returns in Transformation and becomes the independent copies in Arrays. Preserve their established mesh recipe, proportions and material where the lesson does not need those properties to change. Reuse them in tutorial renders and book illustrations as well as in the learner study.

| Family | Recognizable construction | New work on later visits |
| --- | --- | --- |
| Sphere / point | The sphere already made in Point One, packaged as PointBody in Lines | Pickup; endpoints; recording; held resolution change; transformation; copies; colour; rates; forces; waves; later catalyst/weapon abilities. |
| Cube | The learner's indexed cube from Point Animatedcube | Timed transforms; pivot and hierarchy; independent instances; addressed collections; colour assignment. |

Carry the **actual earlier construction**, not an unrelated replacement that happens to have the same name. Explain new behaviour while retaining complete inherited code in the example or its explicitly declared companion files. Keep visual choices fixed during a comparison unless they are the chosen variable. If colour marks a new role or state, name that change; Colour is allowed to teach colour by changing it.

Visual continuity does not require one universal body class. PointBody's frozen pickup settings are not suitable unchanged for a freely moving force receiver. At that transition, preserve the sphere's geometry and appearance, explicitly choose its dynamic body and release/physics settings, and give either the engine or the learner update responsibility. A numerically positioned marker can wear the same sphere geometry without becoming a colliding rigid body. Explain and test that changed responsibility once. Do not create a general inheritance framework merely to obtain consistent pictures.

This is the learner-object plan, not an instruction to replace every museum artifact with a sphere or cube. A plank needed for a crossing, a support plate, a historical work and a distinctive reflective artifact keep their roles. New shapes need a teaching or artistic reason; new chapters alone are not a reason to redesign familiar objects.

### The sphere becomes an instrument

Author direction, 6 October: bring the sphere class back whenever it helps. The student gains an ability by extending an object they already know. Its eventual role is the catalyst and weapon: a means of acting on the world with operations the student can reconstruct. This future role should guide useful returns without loading weapon architecture into the first point lesson.

| Return | New capacity | What must stay explicit |
| --- | --- | --- |
| Godot Primitives | Holding the sphere reduces its rings and radial segments over time. | Same PointBody construction; owned mesh; integer steps; stop at rings 1 / segments 4; collider stays spherical. Release pauses; reset restores. |
| Transformation | Move, turn or scale the familiar sphere through a named action and time rule. | The indexed cube still teaches its existing comparisons. Change the selected object deliberately; identify who owns its transform. |
| Arrays | Make and address independent instances of the sphere class. | Reuse the existing cube array method; distinguish shared construction from shared mutable resources. This is a transfer, not a second introduction to loops. |
| Colour | Give the carried sphere an owned material and apply a returned colour. | Colour is now the chosen changing property. Keep value, material, receiver and the reflective discussion of skin distinct. |
| Change | Follow the same sphere's positions, differences and accumulated movement. | Declare the frame, units, sampling interval and retained record. A prescribed velocity is not an applied force. |
| Forces | Let the sphere carry mass and receive an impulse or force. | Explicitly change frozen pickup/release settings when needed. Select engine or learner integration, never both for the same update. |
| Waves | Make a familiar body oscillate or emit a timed pulse. | Amplitude, period and phase are separate controls; distinguish moving a body from creating a propagating wave. |
| Catalyst / weapon | Activate a learned operation against a valid target and observe its consequence. | Compose named action, target, effect and feedback only after those parts are taught. The production catalyst is source material, not an unexplained dependency. |

These are planned capacities, not claims that cross-hall abilities already persist. Continue the source/version lineage first; name and test any future saved state or transfer of a live instance separately. Each return should carry **inherited object → new operation → observable consequence → behavioural assertion → ability available next**. New representations may need a branch or a small component rather than another responsibility in PointBody.
