Exact points that needed interpretation

  1. lesson.md, “Build another comparison”: “Keep an independent remaining-time value for each point. A two-entry array and the loop pattern above are enough.” The example only assigns a scalar clock. The earlier Trace lesson explains reading and appending entries, but does not demonstrate assigning an existing numeric entry with remaining[i] = .... I inferred indexed assignment and used it both to start and to decrease each clock. This is a small new syntax step that could use one explanatory sentence without giving away the comparison.

  2. lesson.md, “Read the change”: “A greater mass receives a smaller acceleration from the same force.” The text gives three specific speed changes but does not explicitly state acceleration = force / mass or change in velocity = force × duration / mass. I inferred those relationships to predict a new mass and duration. The mass comparison supports the inverse relationship, but the request to calculate a new duration would be clearer with the proportional rule stated explicitly.

  3. lesson.md, “Build another comparison”: “Also predict whether equal final speed puts them at the same distance from their starting places.” The caption requirement later says only “Show both speeds in the caption.” There is no distance readout or sampling instruction, so a student can predict unequal distance but has no specified numerical verification route. I used Launch's position formula, separately for the accelerated and coasting intervals, to predict 1.5 m and 1 m at 2 seconds. My comparison follows the requested two-speed caption and does not add a distance display.

  4. lesson.md, “Build another comparison”: “Use a clear bay, no gravity or damping, and separate the points so they cannot collide during this comparison.” I interpret separation as two parallel free trajectories at X = -1 and X = 1 with force along +Z, rather than adding lane constraints. With 0.14 m radii, they have 2 m of lateral centre separation. This is enough under the stated hands-off conditions. It does not prevent a later grab or external collision from steering one into the other. The lesson's “Model notes” explicitly says the tutorial leaves all three directions available, which supports this choice.

  5. shared-code.md, “Set up once”: “Use your existing PointStudy Node3D in a clear working bay inside each hall”. The supplied museum is sufficient as a dependency, but the packet does not identify a concrete bay placement or unobstructed run length. I assume the parent will install the study where both +Z paths have enough room for at least the two-second comparison and an additional coasting interval. At 3 seconds the faster-starting point has travelled 2.5 m. I did not inspect the hall to choose that placement.

  6. lesson.md, “Read the change”: “Wait for one pulse to end before comparing a second” and “pressing during a pulse restarts its remaining time.” The separate exercise does not restate the two-clock version. I kept that behavior: pressing the shared button assigns both durations again, and does not reset positions or velocities. Fresh numerical trials therefore require restarting the study. Pressing again after the first run adds another 1 m/s to both bodies, given the same hands-off conditions.

  7. lesson.md, “Model notes”: “Godot accounts for the physics time step when applying force.” The packet explains the final partial force step, but does not state when a readout within _physics_process observes the resulting velocity, or what numerical tolerance to use for distance. I treat the caption as an ongoing observation and predict the ideal continuous values. I would not infer a failed force rule from a single displayed frame at the boundary without knowing its sampling time.

  8. lesson.md links such as “Setup and complete shared code” and the links in “What you bring”. Their relative paths refer to the course layout rather than this flat packet. The README and clear filenames allowed me to find the supplied texts. If this packet is intended as a standalone student handout, those links should point at its local files.

Review after the clarification

Ghost student follow-up

I read the revised student-packet/lesson.md and updated my comparison using its instructions. I did not inspect teacher or production sources and have not run engine tests. The original predictions.md is unchanged; the predictions still apply.

My change

comparison.gd keeps each point's initial local position in a start_positions array when it is created. Its caption shows each point's live speed and a distance reading in metres. Until the comparison ends, the distance reading is the length of its current local position minus its saved start. When both clocks first become zero after a press, the code sets snapshot_taken and retains both distance readings. The caption identifies these as the distances when both pushes ended; the speed readings continue updating while the spheres coast.

The started flag prevents the initially zero clocks from capturing a snapshot before the first press. A new press clears snapshot_taken and starts both clocks again. The starting positions remain the original study positions, so the new snapshot on a repeated press measures from those original positions. A fresh comparison requires restarting the study, as Model notes says.

This uses the point's position and its saved start in the same frame. With unit scale and straight, forward paths, the displacement length equals travelled distance. Grabbing a point and making a detour would break that equality; the caption deliberately describes distance from the start, not accumulated path length.

Gaps resolved by the new text

  • Proportional rule: Read the change now explicitly gives acceleration as force divided by mass and velocity change as force times duration divided by mass. My 3 kg / 3 s prediction can be calculated directly from the text instead of inferred from the three examples.
  • Indexed clock assignment: Build another comparison now explains that assigning remaining[i] replaces that clock and that the index must remain paired with its point. This supplies the previously unstated array-editing step.
  • Measuring the distance comparison: The exercise now requires both speeds and distances, tells me to preserve starting positions, gives the displacement-length operation, and connects it to Lines. I could add that readout without looking elsewhere for a solution.
  • Reading the end of the comparison: The latest instruction explicitly requests one snapshot when both clocks first reach zero and suggests a boolean flag that a new press clears. This resolves the earlier concern about trying to read a changing distance after the two-second boundary. I can read the retained values during coasting without confusing them with the current positions.
  • Concrete trial location: Model notes now places PointStudy at (23, 0, 8) in the hall's local coordinates, with zero rotation and unit scale, and asks for four metres of clear +Z space. This resolves where to install the script. I treat it as scene setup rather than assigning that position inside comparison.gd, since the script is attached to the already placed PointStudy.
  • Fresh starts and boundary expectations: The explicit restart instruction makes the fresh-trial procedure clear. Capturing when both clocks reach zero and allowing a small physics-step difference explains why the retained reading need not exactly equal the ideal calculation.

Remaining points

  • The lesson does not define a numerical tolerance or the exact physics-frame observation point. The new qualitative boundary guidance is enough for the proposed observation, but not for deciding a strict pass/fail numerical threshold. I have not supplied one or adjusted predictions to a measured result.
  • The packet still uses course-relative links rather than links to its own flat filenames. README and filenames still make the texts findable, but clicking those references inside this packet is not the stated route.
  • Two-clock behavior on another press remains an inference from the reference's button behavior: both remaining values restart, while velocities and positions remain. The new restart instruction makes this manageable for fresh comparisons, so it is not blocking the exercise.

I continue to assume the supplied helper contract, a stationary unit-scale frame, no grabbing or collisions during measurement, and a clear bay. The two paths at X = -1 and X = 1 remain freely moving and separate under those conditions. I have not verified the bay visually or changed any museum scene.

At 2 seconds, A has travelled 0.5 m during its push and then 1 m during one second of coasting. B has travelled 0.5 × 0.5 × 2² = 1 m while accelerating throughout. I used Launch's displacement rule for each interval. Equal final speeds do not imply equal distances: A was faster throughout the interior of the two-second interval. Its forward lead is 0.5 m at 2 seconds.

For t >= 2 seconds, predicted distances are A = 1.5 + (t - 2) metres and B = 1 + (t - 2) metres. Both retain a speed of 1 m/s; the 0.5 m forward lead remains. Their paths are separated by 2 m across X as well, so neither touches the other in this trial.

Each remaining-time entry reaches zero. Then minf(remaining[i], delta) returns zero and the force branch is skipped for that point. Nothing assigns zero velocity. The supplied free_point.gd sets gravity_scale to zero, replaces linear and angular damping with zero, unfreezes the point, and disables sleeping. The continuing motion assumes no collision or hand interaction.

A new choice: use a 3 kg point with the same 1 N force for 3 seconds. Starting at rest, (1 N / 3 kg) × 3 s = 1 m/s. Its distance when its own push ends would be 0.5 × (1/3) × 3² = 1.5 m. The general duration for a target 1 m/s at force 1 N is numerically equal to the chosen mass in kilograms, expressed in seconds.

These distances are continuous-motion predictions. The lesson delegates integration to the engine, so displayed or measured positions at finite physics steps may differ slightly. I have not observed or fitted any measured result.

Independent construction — inspect after attempting the exercise
extends "study.gd"

var points: Array[RigidBody3D] = []
var start_positions: Array[Vector3] = []
var masses: Array[float] = [1.0, 2.0]
var durations: Array[float] = [1.0, 2.0]
var remaining: Array[float] = [0.0, 0.0]
var distances: Array[float] = [0.0, 0.0]
var started := false
var snapshot_taken := false
var force := Vector3(0, 0, 1)
var reading: Label3D

func _ready() -> void:
    for i in range(2):
        var point = Point.new()
        point.position = Vector3(i * 2 - 1, 1.2, 0)
        point.mass = masses[i]
        add_child(point)
        points.append(point)
        start_positions.append(point.position)
    reading = caption("")
    button("PUSH 1 s / 2 s", Vector3(0, 1, -0.8), push)

func push() -> void:
    started = true
    snapshot_taken = false
    for i in range(2):
        remaining[i] = durations[i]

func _physics_process(delta: float) -> void:
    for i in range(2):
        var point = points[i]
        var interval := minf(remaining[i], delta)
        if interval > 0 and not point.is_picked_up():
            point.apply_central_force(global_basis * force * interval / delta)
        remaining[i] = maxf(0, remaining[i] - delta)
    if not snapshot_taken:
        for i in range(2):
            distances[i] = (points[i].position - start_positions[i]).length()
        if started and remaining[0] == 0.0 and remaining[1] == 0.0:
            snapshot_taken = true
    var distance_heading := "DISTANCE FROM START (LIVE)"
    if snapshot_taken:
        distance_heading = "DISTANCE WHEN BOTH PUSHES ENDED"
    reading.text = distance_heading + "\n1 kg / 1 s: %.2f m/s, %.2f m\n2 kg / 2 s: %.2f m/s, %.2f m" % [
        points[0].linear_velocity.length(),
        distances[0],
        points[1].linear_velocity.length(),
        distances[1]]
