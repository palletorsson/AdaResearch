Random Definition — a making route beside the encounter

The review is useful. Its strongest recommendation is to distinguish reading an instrument from learning to construct and change one.

Adopted

  • Keep the main encounter recognisable. Give the grids before the invitation to choose; give seed one short explanation. Let the bar strips show the offset, then show only the consequential unused request and RGB grouping. Retain “Nothing in a draw says that it is red.” Give the changed colours a moment before explaining replay again.
  • Keep all seven placed artifacts. The textile comparison, number page and crank carry distinct questions; no artifact was demoted or removed. Make the return to the crank deliberate.
  • Build a complete standalone study: one colour, seeded replay, one grid, a matched pair, an unused draw, then equal draws with exchanged channel roles. The final exercise returns to the matched pair first. It does not mix the two experiments.
  • Correct the 13 × 20 layout and column 6, row 6 placement in current companions. Preserve the earlier tutorial and technical account as dated snapshots; move maintenance concerns out of the making route.
  • Narrow the RAND comparison. A stored table and a calculated sequence offer different ways to recover a beginning. Remove the unsupported “last printed table” claim and the seed/table equivalence.
  • Distinguish a fresh configured instance from restored visit state. Source inspection found the actual portal caller, and native checks exercised its save/restore methods.

Implementation finding

During restoration, the instrument replaces its bar-strip nodes. The portal caller previously tried to compute addresses for those removed nodes later in the same traversal. It now checks that a node survives in the scene tree and implements restoration before looking up its saved state. The random generator, hall layout and artifact controls are unchanged.

Look, remember, return

Find a patch in one grid and check the same place in the other. Press REPLAY. Choose a seed with the slider or RANDOM, find another patch, and replay it. The comparison supplies the same integer to both grids:

func _column_seeds() -> Array:
    match comparison:
        "replicas", "offset":
            return [_current_seed, _current_seed]

This is the beginning of a longer function with other comparison modes. The placed room uses replicas.

Before colouring each grid, _regenerate restores the local generator:

_rng.seed = s

Each _rng.randf() call requests one value between zero and one and advances the generator. The returned value has no colour-channel role until the program assigns it one. The code visits the cubes in their construction order, row by row, requesting three values per cell:

for mi in cubes:
    var mat: StandardMaterial3D = (mi as MeshInstance3D).material_override
    mat.albedo_color = Color(
        _rng.randf(),
        _rng.randf(),
        _rng.randf()
    )

Eight rows of eight cubes consume 192 draws. These are material colour values; the room's lighting also affects the colour that reaches the eye. Wait before pressing REPLAY. Elapsed room time does not consume this colour generator's stream: regeneration is requested by controls and configuration changes.

Change the procedure before changing the seed

if _extra_on and i == _columns.size() - 1:

After

Make a colour return

In the room, a seed helped us recover a colour arrangement. Here we will make that return ourselves: give one cube a generated colour, repeat it, then change the result without changing the seed.

This builds on _ready() from Point Zero, arrays and loops from Array, and material colour from Colour. The new tool is a local RandomNumberGenerator. We borrow its internal algorithm, just as we borrow the renderer. What we will control is when it draws and what those draws become. Random Entropy will ask what remains when we count the values instead of keeping their arrangement.

Use the standalone study, with Day Zero's editor and run workflow already in place. Work in study.gd; keep study.tscn as the main scene. display.gd supplies the cubes, one material per cube and a REPLAY button. It does not request random values. Each numbered file in steps/ is a complete version you can copy into study.gd if you lose your place.

1. Give one cube three values

The project opens at this first step. Its complete script is:

extends Node3D

var rng := RandomNumberGenerator.new()

func _ready() -> void:
    $Display.build(1, false)
    replay()

func replay() -> void:
    var cube: MeshInstance3D = $Display.left[0]
    var material: StandardMaterial3D = cube.material_override
    var a := rng.randf()
    var b := rng.randf()
    var c := rng.randf()
    material.albedo_color = Color(a, b, c)

$Display.build(1, false) asks the supplied display for one cube and no second grid. The cube is the first member, [0], of its left array. material refers to that cube's own material. These are the things already prepared for us; the three calls to rng.randf() are our new work.

Each call returns one number between zero and one. Color(a, b, c) assigns them to red, green and blue, in that order. Press REPLAY or Space. The helper calls replay() again; the generator continues from where the previous calls left it. Repetition is possible, but we have given it no instruction to recover a chosen colour.

2. Give the return a beginning

Add this variable beside rng:

var seed_value := 42

Then make this the first line inside replay():

rng.seed = seed_value

Press REPLAY several times. Nothing appears to happen, although the code has requested three values again. Setting the seed puts this generator back at the same beginning. Change 42 to 137 and run again. Keep a colour you like by keeping its seed and this procedure. The complete version is steps/02-seed.gd.

3. Let the array receive the sequence

Change the display request to $Display.build(4, false). It now gives us a 4 × 4 grid. In replay(), keep the seed reset once at the start, then colour each cube:

rng.seed = seed_value
for cube in $Display.left:
    var a := rng.randf()
    var b := rng.randf()
    var c := rng.randf()
    var colour := Color(a, b, c)
    var material: StandardMaterial3D = cube.material_override
    material.albedo_color = colour

The loop reuses Array's ordered collection. Three draws per cube, sixteen cubes: forty-eight values receive a place. The supplied display orders cubes left to right, bottom row first, as the museum instrument does. REPLAY keeps the arrangement. The complete version is steps/03-grid.gd.

Try moving the seed reset inside the loop, just before var a. Every cube now starts at the same three values. Move the reset back outside. Its position changes the pattern without changing the seed.

4. Put two beginnings beside each other

Use steps/04-pair.gd. Its display request is $Display.build(4, true). The same colouring loop is now a function called colour_grid(cubes). replay() calls it once with the left array and once with the right:

colour_grid($Display.left)
colour_grid($Display.right)

The function resets the generator before each grid. Check the same cell on both sides. Press REPLAY and check another. If we reset only once before both grids, the right would continue after the left's forty-eight draws. Equal seeds are useful here because we also keep the requests and their assignment equal.

5. Spend one value without colouring anything

Use steps/05-unused-draw.gd. A skip_first argument tells colour_grid whether to make this extra request, after resetting the seed and before entering the cube loop:

if skip_first:
    rng.randf()

replay() passes false for the left grid and true for the right. The left uses forty-eight draws; the right consumes forty-nine but still gives forty-eight to its colours. REPLAY now recovers the difference too.

Follow the first cube: the left takes (a, b, c); the right takes (b, c, d). No value has changed its position in the generated stream. A different part of that stream is being assigned to each channel.

6. Keep the draws. Change their roles.

Return to the matched pair from step 4, removing the unused draw. This time keep both beginnings equal and swap the right grid's red and blue assignments. steps/06-channel-roles.gd is the complete version. Its loop first constructs:

var colour := Color(a, b, c)

Then, only for the right grid:

if swap_channels:
    colour = Color(c, b, a)

Find a cube with visibly different red and blue amounts. Its green stays the same. Both grids consumed the same forty-eight values. We changed what a value does, without requesting another one.

Choose which comparison you want to keep. Then replace the right-hand assignment with Color(a, a, a): one requested value now supplies all three channels. The other two requests remain in the loop, so later cells still begin at the same place in the stream.

You now have a small construction you can alter: a generator, a repeatable beginning, an ordered array and a choice about what each value becomes. The colour grids are one use of those parts. Their arrangement no longer has to exhaust what the program can do.

State and assignment

_rng is a local RandomNumberGenerator used for colours. Each column resets _rng.seed before assigning one randf() result to each of red, green and blue, row by row. There are 64 cells, 192 assigned channel values per grid. The replicas comparison supplies the current seed to both columns. The implementation and draw procedure determine the repeatability tested here; the seed alone is insufficient to specify an image across changes of generator, version or mapping.

_extra_on causes the last column to discard extra_draws values after seeding but before colouring. The map uses the default of one, so that column consumes 193 draws. It retains the same cell count, meshes and positions. Relative to the unshifted stream, G becomes R, B becomes G, and the next cell's R becomes B. The final blue channel requires the 193rd draw. Replaying preserves this choice; +1 DRAW toggles it. Waiting does not advance this colour generator.

_pick is another local generator, randomized once in _ready. RANDOM requests _pick.randi() % 1000. This menu contains 1000 seed values and allows repeats. No guarantee of a different seed, unique picture for every seed, perfectly equal selection frequencies, or statistical independence is asserted. The separate generator prevents these controls from advancing the game's shared random state.

The slider reads a normalized handle value, clamps it to [0,1] and rounds norm * 999 to an integer. Its displayed range is 0–999 with no decimals. Programmatic changes synchronize the handle. Source configuration can accept integers outside this menu; the handle is clamped to its endpoint while the seed captions retain the actual configured integer. Hall rebuilding restores the configured state, rather than saving the visitor's last chosen seed.
