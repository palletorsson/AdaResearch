# Fresh-context Cellular Automata reconstruction

All eight exact printed programs and all eight independent source variations run successfully in the final checks. No printed program needed a repair. The work establishes executable AI reconstruction and selected transfer evidence; it does not establish human learning, physical headset usability, or the behaviour of every installed exhibit.

The only lesson sources read were the packet's `PREFACE.md`, `order.json`, and the eight ordered `tutorial.md` / `final.md` pairs. The declared `addons/godot-xr-tools` dependency was copied into this isolated student project; its plugin and pickable declarations were read to provide its real autoloads and base class. No production exhibit code, previous student report, old probe, or parent result was used. All created and modified work is under this `student` directory.

## Evidence and execution

`original/` in each hall contains the extracted `student-code` blocks unchanged. `variation/` contains a separately edited copy; `source_variation.diff` makes every source change reviewable. `PREDICTIONS.md` and the per-hall prediction files were written before the first Godot invocation. `pre_run_manifest.json` records the original prediction and test hashes. `integrity.json` compares the final originals with the printed blocks. The preparation generator is retained as the initial preparation record; later fixture repairs are in the working test files and documented in `FAILURES.md`.

`tests/` contains eight self-authored Godot assertion scripts. A neutral `Node3D` host supplies camera, light, background, and a `PointStudy`, using real XRTools classes and the dependency's two autoloads. Synthetic held poses use the printed desktop adapter. Each test runs the actual study and its receivers. Checks include stored arrays/dictionaries, history independence, clocks, MultiMesh transforms and colours, deferred collision, light and globe state, texture pixels/sharing, and selected slice frames. The driver treats a timeout, nonzero process exit, logged engine error, absent checks file, or failed assertion as a failed run. Jobs ran serially with a 45-second runtime timeout, after the parent's GPU-free signal.

Runtime command structure: `Godot_v4.6-stable_win64.exe --path <student> --no-window --rendering-method gl_compatibility --xr-mode off --audio-driver Dummy --log-file <run>/engine.log -- --no-bridges --hall <hall> --variant <original|variation> --run-id <id>`. This is rendered execution, not `--headless`. Each successful run saves a 1280×960 screenshot, engine/stdout/stderr logs, commands, observations, checks, and source/test/harness hashes. `results.json` retains every attempt and exposes each hall's latest result; `SUMMARY.json` is its compact index.

## Failures and their ownership

The first editor import rejected a type inference in my Soft Rules test, and that editor process also ended with access-violation/resource diagnostics. Declaring the test variable fixed the parsing issue; later runtime jobs were clean. The editor shutdown issue was not reproduced or counted as a lesson failure.

The first Introduction runtime caught an overly strict colour comparison in my harness. MultiMesh storage quantizes colour values. A per-component tolerance of `.005` still distinguishes the palettes and accepts that representation. The original failure remains recorded.

During improved screenshot framing, Presence's narrow-radius variation exposed a synthetic-hand timing gap: a pose assigned before an awaited physics frame was not checked again before committing the step. The fixture now settles the transformed parent, resupplies the synthetic hand pose, and asserts it before each update. Both original and variation pass. The exact rigid-body synchronization path of the first failure was not independently traced, so this is recorded as a fixture limitation/failure, not an established book defect. Nothing in either printed script was altered.

The original common camera also framed three miniatures too widely and showed the backing of the Presence frieze. Better fixture views were rendered, preserving the earlier images. All sixteen final screenshots were visually inspected for the intended geometry and receiver states. Some wide-study readouts remain small at this neutral camera; screenshots are supporting evidence, and the saved state/receiver assertions carry the precise claims.

## Reconstruction, progression, and scope of the two texts

The packet was sufficient to reconstruct the programs without guessing hidden children or importing prior CA code. Relative helper paths resolved within each lesson folder. The identical printed PointBody carries construction, pickup adapter, and action signal; it does not carry live state. The preface's Day Zero camera/light/XRTools assumptions made a neutral host legitimate. No missing authored object blocked execution.

The progression is understandable when following the reading routes: ordered Boolean neighbourhood and snapshot, lingering state in a volume, retained history with two consequences, a two-dimensional present linked to a lamp, observer position entering a fractional field, neighbour differences in U/V, cellular update versus recursive placement, then a matched perturbation measured separately from its image. Returning to row engines in lessons three and seven was explicit. The legacy hall names could otherwise mislead, but the text identifies the third lesson as Rule 30 and the fourth as Conway Life.

The supplied/new/carried boundary was mostly precise. MultiMesh furniture and the unchanged PointBody are supplied so the new operation can be isolated. Old-to-next buffering, arrays, address mappings, copying, and coordinate conversion recur as carried skills. The Gray–Scott reaction, recursive placement recipe, and reproducible forcing recipe are explicitly supplied; deriving those systems is not silently demanded. The second hall's smaller seed, sixth hall's different stencil/rates from Shader, and seventh hall's finite recursion depth all prevent false claims of numerical continuity.

The long complete display listings create substantial reading volume, but the named-function reading routes permit a student to keep the staging intact while studying one operation. These tests show that an AI can follow those boundaries and make bounded changes. They do not show how much prior Godot fluency a human reader would need or whether the experience holds their attention.

The tutorials provide construction, local code contracts, controlled changes, and independent tests. The final texts invite movement, attention, comparison, and questions about what a surface permits or conceals. Their installed RUN buttons, rings, curved walls, expanded volumes, walking readers, and bodily consequences are deliberately broader than the reconstructions. I did not interpret these passages as missing implementation requirements. Their philosophical claims were read as interpretive invitations, not outcomes proved by passing code tests.

## Suggested repairs and limits

There is no necessary executable repair to the printed code in this tested scope. One optional documentation improvement would make neutral reproduction easier: in `PREFACE.md`, after the XRTools dependency sentence, explicitly name `XRToolsUserSettings` (`addons/godot-xr-tools/user_settings/user_settings.gd`) and `XRToolsRumbleManager` (`addons/godot-xr-tools/rumble/rumble_manager.gd`). The existing museum already supplies these; the omission was a fixture setup detail, not a reconstruction blocker.

The tests do not exhaust every key binding, every finite budget, every possible seed, performance on Quest, genuine pickup hardware, comfort, locomotion, physical headset interaction, or the larger installations. The optional open composition was not required for the eight-lesson pass and was not attempted. No claim of chaos, proof of universality, human learning, or successful physical walking follows from these runs.

To repeat already-prepared runtime checks, run `python <student>/run_serial.py all --continue`; it appends new run folders and preserves prior attempts. Run `finalize_evidence.py` afterwards to refresh the compact index and integrity hashes. `build_harness.py` is the initial preparation record, not the current repaired fixture source.
