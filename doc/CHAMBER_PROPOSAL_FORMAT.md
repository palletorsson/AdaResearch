# Chamber proposal format

> The chamber is to artifacts what `/dna` is to substrates: a place to *propose
> without polluting*. Each iteration produces a self-contained, portable,
> replayable record. The repo's `dev` branch never sees rejected ideas.

> **Storage:** chamber research material (proposals, patches, captures) lives
> in `ada_encyclopedia/public/chamber-runs/`, NOT in this Godot project. The
> Godot project stays lean; the encyclopedia owns research output. The
> chamber CLI (`tools/chamber.py`) resolves the encyclopedia path from
> `$ADA_ENCYCLOPEDIA_PATH` (defaults to `~/Documents/GitHub/ada_encyclopedia`).

## Concept

Each chamber iteration generates **three artifacts** stored together:

1. **`proposal.md`** — the prompt: human-readable spec, portable across sessions
2. **`changes.patch`** — `git diff` of the speculative apply: machine-applicable, deterministic
3. **`captures/`** — before/after screenshots: visual proof

The prompt is for *reasoning*. The patch is for *replay*. The captures are for *judgment*.
Together they're a complete record. Either alone is incomplete.

## Why this shape

| | proposal.md | changes.patch | captures/ |
|---|---|---|---|
| **Survives codebase drift?** | yes (still meaningful when files move) | no (may not apply cleanly later) | yes |
| **Re-runnable?** | by an LLM (fresh interpretation, may differ) | by `git apply` (verbatim) | not applicable |
| **Re-rateable later?** | yes (read by future humans) | no | yes (visually) |
| **Is the spec?** | yes | no (it's the implementation) | no |

The combination supports three reapply modes:

```
1. Verbatim         git apply changes.patch                    (deterministic)
2. Reinterpret      hand proposal.md to Claude in fresh chat   (creative)
3. Forensic         read both side-by-side                     (calibration)
```

## Directory layout

```
ada_encyclopedia/public/chamber-runs/
├── README.md
├── draft/            ← in-progress, not yet judged
│   └── <artifact>/
│       └── <timestamp>/
│           ├── proposal.md
│           ├── changes.patch
│           ├── context_bundle.json
│           ├── meta.json
│           ├── before/
│           │   ├── front.png
│           │   ├── left.png
│           │   ├── right.png
│           │   └── top.png
│           └── after/
│               └── (same 4 angles)
├── approved/         ← user accepted; ready to apply when desired
│   └── <artifact>/<timestamp>/  (same structure)
└── rejected/         ← didn't work; kept as negative training data
    └── <artifact>/<timestamp>/
        └── (same structure + reason.md)
```

Timestamps are ISO `YYYY-MM-DDTHH-MM` (colon-free for filename safety).

## proposal.md format

```markdown
# Improvement: <artifact_lookup_name> — <short slug>
artifact: <code path, e.g., algorithms/euclideanspaces/point/point.gd>
date:     <ISO timestamp>
sequence: <id> (seq <order>)
maps:     <comma-separated map names that contain this artifact>
identity: "<the @identity essence line, verbatim>"

## What to change
<2-5 sentences. Concrete, testable, specific to this artifact's role.
Reference exact functions/parameters when applicable.>

## Why
@identity essence: "<echo the essence>"
<1-2 sentences connecting the change back to the essence — what does this
let the player feel/understand that they couldn't before?>

## Curriculum honesty
✓ Uses: <techniques referenced in the change> (seq <N> and earlier)
✓ Does NOT use: <random / noise / etc, if applicable> 
   <rule: no random before seq 7, no noise before seq 8, no trees before seq 11>

## Captures
before/{front,left,right,top}.png
after/{front,left,right,top}.png

## Apply with
git apply ada_encyclopedia/public/chamber-runs/<status>/<artifact>/<timestamp>/changes.patch
  OR
/ada-artifact-improver <artifact> --proposal=<path-to-proposal.md>
```

## context_bundle.json — what the artifact starts with

Generated by `chamber.py init`. Contains everything needed to reason about
the artifact without re-discovering it:

```json

  "artifact": {
    "lookup_name": "point",
    "code_path":   "algorithms/euclideanspaces/point/point.gd",
    "scene_path":  "algorithms/euclideanspaces/point/point.tscn",
    "category":    "primitives",
    "identity": {
      "essence": "...",
      "desire": "...",
      "critical_parameter": "...",
      "triggers": "...",
      "emerges": "...",
      "needs": "...",
      "relationships": "...",
      "truth": "..."
    }
  },
  "placement": {
    "sequences": [{"id": "primitives", "order": 1, "name": "..."}],
    "maps":      [{"name": "P_Point", "position": [3, 1, 5]}],
```

## meta.json — chamber state

```json
{
  "lookup_name": "point",
  "timestamp":   "2026-05-06T14-23",
  "status":      "draft",          // draft → approved | rejected
  "created_at":  "2026-05-06T14:23:00",
  "claude":      "Sonnet 4.x",
  "rating":      null,             // populated on approve: gold | silver | bronze
  "decision":    null,             // populated on approve/reject
  "decided_at":  null,
  "worktree":    ".claude/worktrees/chamber-point-2026-05-06T14-23"
}
```

## reason.md — only on rejection

```markdown
# Why rejected: <artifact> — <slug>

## What didn't work
<1-3 sentences. Visual? Conceptual? Curriculum violation? Performance?>

## What to try instead
<optional: an alternative direction>

## Tags
<one or more: visual-cluttered | curriculum-broken | performance-cost |
              concept-mismatch | already-tried | needs-other-system>
```

The rejected dir is **negative training data** — preserved precisely because the
attempt didn't work. Patterns in rejection reasons surface what categories of
proposal don't fit this project.

## Competitive auto-research — N candidates per iteration

A single iteration can explore *multiple* approaches in parallel. Three
extra commands plus a new `alternatives/` state run the loop:

```
explore <artifact> [-n 3] [--directions=behavior,visual,narrative]
                                                 │
                                                 ▼
   draft/<artifact>/<ts>/                        ← scaffold
     shared_context_bundle.json                  one bundle, all candidates read it
     shared_meta.json                            status="exploring", candidate_count, directions
     before/                                     shared BEFORE capture (auto-AABB)
     candidate_1/   direction.md, meta.json      ← worktree per candidate
     candidate_2/   direction.md, meta.json
     candidate_3/   direction.md, meta.json
                                                 │
   [Claude edits each worktree differently]      │
                                                 ▼
finalize-explore <artifact>
                                                 │
                                                 ▼
   each candidate_*/                             ← captures + patches written
     changes.patch                                  (with locked framing — fair diff)
     after/{4 angles}.png
     proposal.md  (scaffold; Claude fills)
     score.json   (rubric template; Claude fills)
   comparison.md                                 ← umbrella verdict scaffold
                                                 │
   [Claude fills score.json + comparison.md      │
    with rubric reasoning + verdict]             │
                                                 ▼
promote <artifact> --winner=<i> [--rating=gold]
                                                 │
                                                 ▼
   approved/<artifact>/<ts>/                     ← winner flat-copied (normal flow)
     proposal.md, changes.patch, before/, after/
     meta.json   (status=approved, promoted_from=alternatives/.../candidate_<i>)
     alt_summary.md  (linkback to full comparison)

   alternatives/<artifact>/<ts>/                 ← whole set kept as comparative record
     comparison.md
     before/, candidate_1/, candidate_2/, candidate_3/
     winner.txt   (just "candidate_<i>")
```

The winner appears in `approved/` so existing apply paths and the `/chamber`
page see it as any other approval. The full record (winning + losing
candidates, side-by-side captures, rubric scores, the verdict) lives in
`alternatives/` as comparative training data — far more valuable in
aggregate than a single approved proposal alone.

### Score rubric (per candidate)

| Rubric | What it weights |
|---|---|
| visual_clarity | does it read in 4-angle captures? is the artifact's *what-it-is* legible? |
| curriculum_honesty | uses only what's unlocked at this sequence |
| narrative_fit | deepens or contradicts the @identity essence |
| novelty_vs_project | echoes existing patterns (good — composability) or duplicates them (bad — drift) |
| performance_cost | draw calls, LOD, frame-time impact |
| reversibility | patch size + file count; future iterations can undo cleanly? |

Each candidate's `score.json` records both the per-rubric scores and the
list of context sources Claude read while generating that candidate. Over
time the corpus answers: *which kinds of context produced winners?*

### When to use explore vs init

- **`init`** — single-approach iteration. Use for clear small fixes,
  refactors with one obvious shape, or when the design is already decided.
- **`explore`** — multi-candidate iteration. Use for high-stakes artifacts
  (canonical primitives, on-spine artifacts, anything referenced widely),
  when the design space is open, or when previous iterations on the
  artifact have left genuine alternatives unresolved.

## Lifecycle

```
init        ──► ada_encyclopedia/public/chamber-runs/draft/<artifact>/<ts>/
              + worktree at .claude/worktrees/chamber-<artifact>-<ts>/
              + before/ captures
              + context_bundle.json
              + meta.json (status: "draft")

[user / Claude proposes change in worktree, runs after-capture]

finalize    ──► writes changes.patch (git diff in worktree)
              + after/ captures
              + proposal.md
              (still in draft)

approve     ──► moves draft/<...>/ → approved/<...>/
              + meta.json status: "approved"
              + (optional) git worktree remove

reject      ──► moves draft/<...>/ → rejected/<...>/
              + reason.md
              + meta.json status: "rejected"
              + git worktree remove (always — rejected = no further work)
```

## Curriculum honesty as a guard

Every proposal must declare which curriculum techniques it uses, and the
honesty rules from `commons/biome_layers/biome_contributions.json` constrain
what's allowed at each sequence position:

| Before seq | Cannot use |
|---|---|
| 7 | `randf()` / random anything |
| 8 | Perlin/Simplex/any continuous noise |
| 9 | cellular automata |
| 10 | recursive subdivision / fractals |
| 11 | L-systems / branching grammars |
| 12 | DNA / generative procgen |
| 13 | soft-body physics |
| 14 | flocking / swarm behaviour |

A proposal that uses noise at seq 4 should be auto-rejected before captures.

## How a future session uses this

```bash
# 1. Pick an artifact and seed a draft
python tools/chamber.py init point

# 2. Read context_bundle.json — understand what the artifact does and where it sits
cat ada_encyclopedia/public/chamber-runs/draft/point/2026-05-06T14-23/context_bundle.json

# 3. (As Claude in a session) edit point.gd in the worktree
#    .claude/worktrees/chamber-point-2026-05-06T14-23/algorithms/.../point.gd

# 4. Capture and finalize — produces changes.patch + after/ + proposal.md
python tools/chamber.py finalize point

# 5. Review locally (open the captures, read proposal.md)
# 6. Approve or reject
python tools/chamber.py approve point
   # OR
python tools/chamber.py reject point --reason="visual cluttered, breaks readability"
```

The chamber is designed so Claude doesn't have to read a long conversation
to pick up where someone left off — `context_bundle.json` is the entry point
for fresh reasoning, the worktree is the staging ground, and the proposal/patch
are the output.
