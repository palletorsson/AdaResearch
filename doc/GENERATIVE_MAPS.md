# Generative Maps — maps as seeds, not files

> **What this is.** The design + running status of Ada's map generator: instead of hand-authoring
> `map_data.json`, you give a small **seed** and the map generates. This doc mirrors a design arc
> that previously lived only in Claude's session memory, so it's discoverable in the repo and
> reviewable alongside the commits.
>
> **Code:** [`tools/kernel_map.py`](../tools/kernel_map.py) · [`tools/spine_corridor_generate.py`](../tools/spine_corridor_generate.py) · [`tools/structure_recipes.py`](../tools/structure_recipes.py)
> **Commits:** `516a7bf92` (jitter) · `7768554cc` (kernel) · `424f508d1` (exceptions + bag)

---

## 1. The idea

Shift from static, hand-authored maps to an **autogenerated** system: you decide a small seed
`{ artifacts[], separation }` and the map generates. A map is a **seed you run**, not a file you
store — store the seed, compete on the depth of the run (the project's compression/queer thesis,
"the deep" = a short seed with a costly, irreversible run).

**One generator, three views:** the same generator emits one `map_data.json` that serves a **VR
walk** (the headset, via SpineRunner), a **web view** (`/editor` + `/api/maps` in the
encyclopedia), and a **headless capture**. Web and VR are not two pipelines — they're two views of
one file.

---

## 2. The grammar: function (fixed) vs expression (per-sequence)

- **FUNCTION** (invariant for every map): the sequence's **content** at real footprints · a
  **walkable START→END** route past all of them · **encounter order = curriculum order** · the
  **5-phase arc** (entry → teaching → exploration → reflection → exit).
- **EXPRESSION** (per sequence): **relations** (cluster / isolate / wall-back) · **character**
  (topology / jitter / density) · **tectonics** (levels / voids / derived slopes + bridges).
- **Validation by profile, not by replica:** measure authored maps (walkability, encounter order,
  density, clustering, level variation, phase presence) and tune the generator until generated maps
  hit the same **profile** — they should feel like a sibling, not a copy.

## 3. The kernel (`tools/kernel_map.py`) — four rules

**Policy: default 9 wide, default flat. The artifact is the only source of exceptions.**

1. **FOOTPRINTS** — each artifact occupies its measured AABB in cells (`measurements.aabb_size`,
   ceil of x,z; fallback `spatial_needs.footprint_cells` → √).
2. **PACK** from (0,0) with separation `s` (the walking gap), deepest-first into shelves.
3. **SIZE** — width = 9 by default; depth follows from the pack. An artifact widens it *only* to
   keep a walking lane (`W = max(9, widest + 1 + s)`); a too-wide item is rotated long-side along
   depth.
4. **PATHFIND** — BFS guarantees a walkable START→END route reaching past every footprint (this
   guard is what catches an artifact that would wall the map).

**Seed = `{ artifacts[], s }`.** Width and relief are 9/flat unless an artifact says otherwise.

```bash
# borrow a map's artifact bag:
python tools/kernel_map.py --map Point_One
# YOU decide the artifacts (the real "maps as seeds" use case):
python tools/kernel_map.py --bag point,vector_addition,vector_field --s 1
# emit a game-valid map_data.json:
python tools/kernel_map.py --map Point_One --out commons/maps/Point_One/map_data.kernel.json --name Point_One
```

`--out` writes canonical **compact-rows** `map_data.json` (3 layers + spawn `#sp` + teleport `t`,
including the catch-floor teleport convention). The game's own `python tools/map_pathfinder.py check`
passes clean on the output — i.e. the engine accepts it and it's VR-loadable.

### Artifact exceptions (the only knobs — all read from the registry's `spatial_needs`)

| Field | Effect |
|---|---|
| `platform` | `pedestal`/`table` → plinth (height 2); `sunken` → pit (height 0); else flat (1). Relief is confined to **obstacle** cells, so the walking floor stays flat and walkability is preserved. |
| `wall_backing` | a raised (height 3) backing panel behind the artifact, in the inter-shelf gap. |
| `isolation` (0–3) | extra walking gap around the artifact. |

## 5. STEP 7 (NEW) — systems & flow: render the graph's *edges*

STEP 6 places the graph's **nodes** (artifacts, clustered by distance). The **systems layer**
renders its **edges** — and completes the artifact's spatial identity alongside packaging.

Two duals:

- **Invisible system = the movement graph (negative space).** The player flows through the **void**
  — which is exactly the kernel's Rule 4 / `tools/walk_evaluator.py`. **It is never rendered.**
  (Drawing the player's own graph on the floor turns a space into a flowchart and kills it — the
  void is the generative habitat.)
- **Visible systems = infrastructure through the solids** (power · fluid · data · drainage ·
  robot-rail · bridge). Each is a **typed graph with a direction and a flow**, rendered as
  pipes / cables / light-on-floor between connected artifacts. A machine is a **source**, a
  table-with-a-screen is a **sink**, and the conduit between them is a designed **edge**.

A tile stops being one thing and becomes a **stack of cross-sections**: floor (power strip /
drainage) · wall (conduit) · ceiling (big pipes / data) · void (people). The same footprint reads
differently depending on which system you trace.

**Most of it is already latent** — STEP 7 is mostly *rendering an existing graph*:
- `spatial_needs.cluster_with` is already an **edge list**.
- the artifact-distance Atlas (`tools/artifact_embed.py` → `artifact_atlas.py`) and the ten concept
  maps are already the **weighted graph**.
- `utilities` already carries visible edges (transport cubes, ramps, bridges).

So the work is: (a) **type** the edges (`kind: power | fluid | data | drainage | rail | bridge`),
(b) a `HangarKit`-style `system_edge(from, to, kind, flow)` renderer in
[`commons/artifacts/_hangar/`](../commons/artifacts/_hangar/), (c) let the placement hook **route +
spawn** edges between placed nodes (the generator already knows node positions).

**Pairs with the packaging family** (`commons/artifacts/_hangar/`, `registry/packaging.json`):
packaging = node ↔ **ground**; systems = node ↔ **node**. Together they give an artifact its full
place in the room.

**Caveats (run it through the Sieve):**
- *Q2 — what's foreclosed?* In a dead / post-collapse facility, flow is **scarce** — one live
  trickle through a mostly-dead net. Lighting every cable makes a sterile Christmas-tree flowchart.
  Scarcity of flow is both the mood and the legibility.
- *Q3 — the dark spot:* keep the **movement graph invisible**; let dead/severed/ambiguous edges
  stay dark. The unlit parts are the generative habitat.
- Apply systems where the **subject is flow** — vector fields, `flow_field`, L-systems (transport
  networks), procgen, the post-crisis **rhizome** — so the map teaches by *being* the network.

**The keystone — `needs`.** The one addition that unlocks the rest: declare what each artifact
**needs** and the building derives from it. `commons/artifacts/_hangar/needs_model.gd`
(`NeedsModel.infer`) returns `{power, fluid, data, vent, waste : bool · load : 0..2 · hangs}` from an
artifact's tags/category/lookup (explicit `spatial_needs.needs` overrides). The compression seed:
*needs in, building out.* Without it the generator can only pack; with it, it can reason.

**First slice — BUILT** (commit `578b0fc29`, `commons/artifacts/caused_room/`): one logical room
where the reactor's inferred needs *cause* the build — `load`→a supported slab, `power`→a lit floor
strip from a wall source, `vent`→a pipe to the ceiling; the screen (`power`+`data`) gets a power edge
+ a data line and reads "POWER ON". The edges render via `HangarKit.system_source(kind)` +
`system_edge(a, b, kind)`. The grammar generalises from here to pipes / drainage / rails.

**Generation is now CAUSED** (commit `8d5f82dfb`):
- `tools/infer_needs.py` → `doc/artifact_needs.json` — inferred needs for all **2548** artifacts
  (power 249 · data 113 · vent 158 · fluid/waste 19 · load-2 748). Derived/regenerable; `--apply`
  bakes into `spatial_needs`.
- `tools/kernel_map.py` reads the catalogue, **raises heavy artifacts (load≥2) onto a supported
  slab**, and emits a **`systems` block** in the `map_data.json` — one **source** per active
  life-support kind on the boundary + an **edge** from it to every artifact that needs it. Verified:
  a 5-artifact bag → 9×22, `path_ok`, 5 sources / 9 edges, and `map_pathfinder check` still clean.
- `commons/testing/render_systems.gd` renders a generated map's `systems` block via `HangarKit`
  (power/data = lit floor strips, vent/fluid = overhead pipes) — the generation→data→render proof.

**In-engine render — DONE, gated** (commit `9a75d7902`): `GridInteractablesComponent.render_map_systems()`
(called once from `GridSystem._on_interactables_complete`) renders a loaded map's `systems` block as
visible flow — gated by the runtime flag **`systems_render`** (default OFF in `ada_run/runtime_flags.json`,
same mechanism as `artifacts_enabled`), reload-safe. Verified: `Kernel_Sys_Demo` loaded via
`capture_multi_angle --mode=map` renders the sources + pipes/strips in-engine. **To walk one:** set
`"systems_render": true` in `ada_run/runtime_flags.json` and load a kernel-generated map.

**Remaining:** tune the floor-Y for non-flat maps; let the gated placement hook spawn sources/edges
alongside packaging; pulse the flows; and make most edges *dead* (the scarce-flow ruin aesthetic).

  files) → a fully endless, generated spine.
