## Confirmed local behavior gap

**Update, 20 September:** [The rack input pilot](../rack-input-pilot/README.md) repairs both controls and verifies the module-face GUI route. The census observations and probe below describe the earlier state and are retained as baseline evidence. The separate standalone wrapper still needs pointer forwarding.

At the time of this census, the stepped and bipolar 2D rack sliders extended `RackControlBase`, whose pointer press/drag handlers were empty. Unlike `RackSliderH` and `RackSliderV`, neither overrode them.

A Godot headless probe instantiated all four controls and directly called their press and drag handlers after setting the value to 0.1:

| Component | Before | After |
|---|---:|---:|
| `RackSliderH` | 0.1 | 0.40625 |
| `RackSliderV` | 0.1 | 0.93590 |
| `RackSliderStepped` | 0.1 | 0.1 |
| `RackSliderBipolar` | 0.1 | 0.1 |

This verifies a component-level difference. It does not test GUI event delivery, VR ray hits, reach, a consumer supplying its own input, or headset use. The stepped slider currently quantises its **drawing**; that alone does not quantise input or emitted values. The bipolar slider draws a signed scale; its own script does not implement the center-return behavior described in its header.

Evidence: [probe result](../rack-handler-probe.json), [probe source](../probe_rack_handlers.gd), [engine log](../rack-handler-run.log). Godot exited successfully. Startup still logged the previously observed UID and certificate-store errors, plus the expected missing WorldEnvironment warning in this bare harness; no probe script errors appeared.

**First actionable improvement:** implement and verify press/drag behavior for these two controls, decide and document their value and release contracts, then compare them with the 3D snapped and zero-return sliders. Promote them into the master demonstration only after that behavior is verified.

## What remains unproven

- Static scanning cannot enumerate every runtime loop, generated program, assembled load path, mesh-based hit target or optional configuration. The inventory keeps unresolved cases instead of calling them missing controls.
- Dependency tracing can include helpers and optional scenes that are not instantiated. An empty family list means no recognised evidence, not proof of no interface: a palm scanner, for example, is a bodily interface outside the button/slider/screen recognisers.
- Registry files contain 20 duplicate keys; 10 name differing scene paths. The inventory preserves both possible definitions. These are registry-wide findings, not necessarily interface defects.
- Reach, legibility, occlusion, target size, feedback, reset behavior and Quest performance still need tests at actual player positions. No new headset playtest was performed.

See the [method and review workflow](../inventory-method.md) for evidence definitions and exclusions, and the [principle coverage plan](../coverage-plan.md) for integration priorities. No production controls or game scenes were changed by this audit.
