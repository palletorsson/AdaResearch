Concept: A QA/test lab for the console interface work — the Shannon desktop console and the standalone control_console placed alongside five migrated workbenches so the unified UI can be exercised in a VR walkthrough.
Sequence role: A development/test map in the Forces sequence, not a player-facing teaching step. Its purpose is to verify the console UI across several visualizations before that UI is trusted in the real teaching maps. No difficulty progression; it exists for the maintainer walking the build, not the learner walking the curriculum.
Technical angle: control_console and the Shannon desktop console (shannon_workbench) under test, plus migrated workbenches that mount domain visualizations on the shared console — cantor_diagonal_workbench (Cantor's diagonal argument), riemann_sum_workbench (Riemann integration), tangent_slope_workbench (derivative as slope), triangle_curvature_workbench (discrete curvature). The map is a harness for confirming consistent slider/panel behavior across these.
Critical angle: A test lab in the sequence is honest infrastructure — it admits that the interface is itself an artifact that must be validated, not assumed. The same flattening noted for Reformed_Instruments applies: Cantor, calculus, and curvature all reduced to one console is efficient for testing but says nothing pedagogical; here that flattening is appropriate because the subject is the console, not the math.
Key artifacts: control_console and shannon_workbench are the interfaces under test; cantor_diagonal_workbench, riemann_sum_workbench, tangent_slope_workbench, and triangle_curvature_workbench are the migrated visualizations exercising that interface.
Gap: This is a test map living in the player-facing Forces sequence — it should likely move to a dedicated tools/test sequence (or be flagged non-curricular) so it does not appear in a learner's journey. If it stays, a visible "TEST LAB" marker at spawn would set expectations honestly.
