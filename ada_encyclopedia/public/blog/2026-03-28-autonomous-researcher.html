The Autonomous Researcher

AI That Thinks Before It Acts

Most AI assistants wait for instructions. You say "fix this," they fix it. You say "build that," they build it. But research doesn't work that way. Research means navigating an unknown space, noticing what's wrong, reasoning about what to do, and only then acting. We built an AI agent that does exactly this — and the key insight was forcing it to think slowly.

I. The Problem with Reactive AI

A typical AI coding session looks like a conversation: the human identifies a problem, the AI solves it, the human identifies the next problem. The intelligence about what matters lives entirely in the human's head. The AI is a fast typist with good taste.

This breaks down when the project is large enough that no single person can hold it all. Ada Research has 752 artifacts, 656 maps, and 42 sequences. There are broken pipelines, missing screenshots, untested maps, and theory gaps scattered across all of it. No human can audit this in a sitting. But an AI that can navigate the project autonomously? That's a different proposition.

The shift from reactive to research AI is not about intelligence. It's about agency — the ability to decide what to work on, not just how to do it.

II. The Cycle: ORIENT → ASSESS → THINK → ACT → VERIFY → RECORD

The autonomous researcher runs a six-phase cycle. Each phase has a distinct purpose, and none can be skipped.

1. Orient

Where am I?

The agent surveys the project at a high level. It checks coverage dashboards, reads recent commits, and identifies which areas have the most gaps or the most recent activity. It picks a direction before looking at any code.

2. Assess

What needs improvement?

Now the agent drills into the chosen area. It runs validation tools, checks for missing captures, looks for maps without pathfinder results. It builds a ranked list of problems by severity: compile errors first, then broken pipelines, then missing content, then polish.

3. Think

What should I do about it?

This is the critical phase. The agent writes out its reasoning: what it found, what options exist, what the tradeoffs are. It must consider at least two approaches plus "do nothing." It picks the option with the highest value-to-risk ratio.

4. Act

Make the change

Only now does the agent touch files. It follows existing patterns — the artifact creation template, the blog CSS theme, the map data schema. Small, targeted changes. No refactors unless they're justified by the thinking phase.

5. Verify

Did it actually work?

Every change gets checked. Run the pathfinder. Capture a screenshot. Parse the GDScript for errors. If verification fails, the agent returns to the Think phase with new information — it does not retry blindly.

6. Record

What did I learn?

The agent writes down its discovery. Not just what it changed, but what it learned — the reusable insight that future sessions can build on. This is how institutional knowledge accumulates instead of evaporating between sessions.

III. Why Slow Thinking Matters

The Think phase is the entire point. Without it, the agent degenerates into a pattern-matcher: see problem, apply template, move on. That works for routine fixes but fails catastrophically for anything novel.

Consider a concrete example. The meander tile editor can compose floor patterns on the web, but the Godot artifact still uses hardcoded bitmaps. A reactive AI, asked to "fix the meander pipeline," would immediately start editing the GDScript. A research AI pauses:

THOUGHT: The web editor produces composition JSON.
The Godot artifact reads hardcoded bitmaps.
Option A: Update the Godot artifact to read composition JSON.
  Pro: Direct pipeline. Con: Couples Godot to web format.
Option B: Create a translation layer that converts JSON to bitmaps.
  Pro: Preserves existing Godot code. Con: Extra complexity.
Option C: Do nothing.
  Pro: No risk. Con: Pipeline stays broken.

I choose A because the composition JSON is already the source
of truth. Reading it directly is simpler than maintaining a
translation layer that exists only to preserve old code.

The thinking takes seconds. But it prevents the kind of decisions that create technical debt — the translation layers, the compatibility shims, the "temporary" bridges that become permanent.

Forcing an AI to write down its reasoning before acting is not a bureaucratic overhead. It is the mechanism by which the AI does research instead of code generation.

IV. LOD Enables Autonomous Navigation

A research agent needs to navigate. Not just read files, but understand where it is in a large project and decide where to go next. This is what the Level of Detail system provides.

Without LOD

The agent loads everything into context, runs out of space, and loses track of the big picture. Or it loads too little and misses the real problem.

With LOD

The agent starts at Level 0 (project overview), drills to Level 2 (sequence detail) where it spots a gap, then zooms to Level 4 (individual artifact code) to fix it.

LOD gives the agent the same capability a human researcher has when they skim a table of contents, notice a weak chapter, and open to that page. The fractal structure of the context — overview, area, topic, detail, code — mirrors the fractal structure of understanding itself.

The agent doesn't need to hold 752 artifacts in memory. It needs to know that sequence 12 has 80% coverage and sequence 37 has 40%, so it should probably look at sequence 37. That's a Level 0 fact. The details come when the agent decides to zoom in.

Navigation is not a prerequisite for research. Navigation is research. Choosing where to look is the first intellectual act.

V. Research AI vs. Reactive AI

The difference is not capability. Both can edit files, run tests, and write code. The difference is in who decides what to work on.

Reactive AI

Human identifies problem.

AI implements solution.

Human checks result.

Human identifies next problem.

Loop.

Intelligence: in the human.

Research AI

AI surveys the landscape.

AI identifies problem.

AI reasons about options.

AI implements and verifies.

AI records what it learned.

Intelligence: distributed.

This doesn't replace the human. The human sets the direction, defines what "good" means, and intervenes when the agent is stuck or heading somewhere wrong. But the mechanical work of auditing, finding gaps, and fixing routine problems? That can run autonomously.

The guardrails matter. The researcher agent stops after 5 improvements. It stops when stuck for 2 iterations. It never modifies core systems without asking. These limits are not weaknesses — they're what make autonomy safe enough to be useful.

VI. What We Learned

Three things surprised us building this system:

1. The thinking phase is cheap but transformative

Writing a THOUGHT block adds maybe 10 seconds to a cycle. But it catches bad decisions that would cost hours to undo. The return on investment is extraordinary.

2. Recording is harder than acting

It's easy to fix a bug. It's hard to articulate what you learned from fixing it in a way that helps the next session. The Record phase forces the agent to extract reusable knowledge — which is the actual output of research.

3. Stopping is a skill

An autonomous agent that never stops is a liability. The decision to stop — because the fix needs VR testing, because the problem is deeper than expected, because five improvements is enough for one session — is as important as the decision to act.

The measure of a research agent is not how much it can do in a session. It's how much it can learn.

The autonomous researcher is not a replacement for human thinking.
It is a tool for extending human thinking into spaces too large to audit alone.
