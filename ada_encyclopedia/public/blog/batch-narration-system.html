Batch Map Narration

March 16, 2026

Ada Research has around 500 maps spread across 19 curriculum sequences. Each map is a hand-authored grid of walkable tiles, walls, artifacts, and a teleporter to the next level. Until now, the only way to know if a map actually worked — if the player could reach every artifact, find the exit, and not get stuck in a dead end — was to load it in VR and walk it yourself.

Today we built a system that walks every map automatically, narrates what it sees, and reports problems across the entire curriculum.

What SceneNarrator Already Did

We had an autoload called SceneNarrator — a perception system that watches the active GridSystem and produces two documents when a map loads:

Spatial Analysis — the geometry. Dimensions, room detection, height profile, where artifacts sit in space.
Journey Narrative — the experience. BFS from spawn, which artifacts you hit in what order, pacing density, dead-end analysis.

This worked well for one map at a time. Load a map in the editor, SceneNarrator generates its markdown report. But running it on 500 maps by hand? That's not a workflow, it's a punishment.

The Batch Runner

The new narrate_all.gd script extends SceneTree (the same pattern as our existing screenshot capture pipeline) and iterates the entire curriculum spine automatically:

godot --path . --xr-mode off --no-window \
  --script res://commons/testing/narrate_all.gd -- \
  --outdir=res://ada_run/narrations \
  --sequence=cellularautomata \
  --wait=3

Per-Map Pipeline

1 Read curriculum_spine.json → ordered sequence list
2 For each sequence, load sequences/<name>.json → ordered map list
3 Instantiate GridSystem, connect generation signal, add to tree
4 Wait for map_generation_complete signal (with timeout fallback)
5 Disable artifact processing (prevent simulation loops from starving timers)
6 Force SceneNarrator to reconnect, collect spatial + journey data
7 Write per-map files, tear down GridSystem, move to next

For each map, the runner writes three files into ada_run/narrations/<sequence>/<map>/:

Markdown (Human)

  • scene_spatial.md
  • journey_narrative.md

JSON (Machine)

  • narration.json
  • narration_report.json (global)

Issue Detection

The journey analysis doesn't just describe — it diagnoses. BFS from spawn classifies every tile as reachable or unreachable, and flags five categories of problem:

critical No spawn point found
critical Teleporter unreachable from spawn
high Artifact unreachable from spawn
low High dead-end count (>3)
low Poor pacing density (too sparse or too dense)

These get aggregated into a global report: which sequences have the most issues, which maps need attention first, and a cross-curriculum health score.

The Timer Starvation Bug

The hardest problem was invisible. Maps CA_1 through CA_10 narrated fine. CA_12 hung forever.

The culprit: three cellular automata artifacts in CA_12 — disease_spread_ca, self_organization_ca, and ca_screen — each running a 64×64×64 grid simulation in their _process() callback. Every frame, they iterate 262,144 cells. The frame budget exploded to seconds. Godot's SceneTreeTimer couldn't fire because the frame never finished fast enough for the timer resolution to matter.

The fix was blunt but effective: after grid generation completes, recursively disable _process() and _physics_process() on every child node of the GridSystem. The narrator only needs the static geometry and artifact positions — it doesn't need simulations running.

func _disable_processing_recursive(node: Node) -> void:
    node.set_process(false)
    node.set_physics_process(false)
    node.set_process_internal(false)
    node.set_physics_process_internal(false)
    for child in node.get_children():
        _disable_processing_recursive(child)

The Phantom Spawn Problem

After fixing the timer starvation, the next run completed all 12 CA maps. But the results were wrong: CA_1 found 3 artifacts, CA_2 through CA_12 found zero. Every map after the first reported "No spawn point found" as a critical issue.

SceneNarrator detects the spawn by looking through utility_objects — the instantiated scene nodes that represent spawn markers, teleporters, and other gameplay utilities. It searches for anything with "spawn", "move", or "start" in the name. The problem: most maps in Ada Research don't have an explicit spawn utility. Players arrive via teleporter from the previous map. Only the first map in a sequence has a m: (MovePlayer) entry in its utilities layer.

Without a spawn position, the BFS can't start. No BFS means no reachability analysis, no artifact distances, no pacing density. The entire journey narrative collapses.

The fix was a three-tier fallback chain:

1 Check instantiated utility nodes for spawn/move/start names
2 Read raw map_data utilities layer for m: or s: tokens
3 Fall back to the first walkable floor tile in the grid

The same pattern was applied to teleporter detection — check instantiated nodes first, then fall back to reading t: tokens from the raw utilities layer. This matters because in batch mode, the narrator often runs before all utility nodes have finished initializing, but the raw map data is always available immediately after the data component loads.

After adding these fallbacks, the results transformed: CA_2 went from 0 artifacts to 4. Maps that were invisible to the system became fully analyzable.

The Signal Timing Bug

A subtler problem: the generation wait loop was counting elapsed time by incrementing a counter each time a create_timer(0.5) fired. Normally fine. But when a CA artifact's _process() takes 10 seconds per frame, a 0.5-second timer fires once per frame — but the counter only increments by 0.5, not by 10. A 15-second timeout could take 300 real seconds to trigger.

The fix was to use wall-clock time instead:

var wait_start: int = Time.get_ticks_msec()
var timeout_ms: int = 10000
while not _map_generated and (Time.get_ticks_msec() - wait_start) < timeout_ms:
    await create_timer(0.25).timeout

There was also a lambda capture issue — GDScript lambdas captured the generated boolean but the signal callback wasn't reliably modifying it across coroutine boundaries. Switching to a member variable (_map_generated) with a named callback method fixed it. Total run time dropped from 200 seconds to 44.

Encyclopedia Bridge

The narration report isn't a dead document. A Python bridge script reads the JSON report and connects it to the Ada Encyclopedia:

# Read report, generate improvement proposals
python tools/narration_to_encyclopedia.py \
  --report ada_run/narrations/narration_report.json \
  --encyclopedia http://localhost:3003

The encyclopedia exposes a GET /api/game/narration-report endpoint that serves the latest batch narration data. The bridge script reads the report, maps each issue type to a concrete improvement action, and can POST proposals back to the encyclopedia for map-by-map refinement.

Issue → Action

  • unreachable_teleporter → add path or ramp
  • unreachable_artifact → add floor tiles
  • sparse_pacing → add more artifacts
  • high_dead_ends → add connecting corridors

Data Flow

  • Godot → narration_report.json
  • Python → improvement_proposals.json
  • Encyclopedia → GET /api/game/narration-report
  • Encyclopedia → POST /api/game/narration-report

What This Unlocks

Batch narration is foundation work. With structured per-map data across the entire curriculum, we can now:

Regression testing. Run narrate_all after every batch of map edits. If a previously clean map develops an unreachable teleporter, the report catches it immediately.

Curriculum analytics. How does pacing density vary across the spine? Are early sequences too dense and late ones too sparse? The aggregated data answers questions we couldn't ask before.

AI-assisted map repair. The improvement proposals feed directly into the encyclopedia's map generation API. An AI agent can read the issues, propose fixes, and validate them through the same pipeline — closing the loop.

Progress tracking. A daily narration run becomes a health dashboard. The report JSON is machine-readable; any CI system or monitoring tool can parse it.

  POST /api/game/narration-report → stores improvement proposals

Three new files, two modified. No new dependencies. The entire system runs headless on a machine without a display. The hardest part wasn't the architecture — it was learning how Godot's frame loop behaves when an artifact decides to simulate 262,144 cells every tick.
